# Documents have one place in nested folders

Device-local organization lives in `library-folders.json`, keyed by stable Folder ids and Document ids, rather than in the shared Positions File or filesystem paths. The owner explicitly chose local-only folders (#121, design 0069); adding folder fields to the shared format would couple ordinary organization to Zotero compatibility. Existing Library entries have implicit root membership, so no Document identity, position or audio migration is required.

The folder store validates the entire hierarchy and refuses unknown versions, unknown fields, missing parents and cycles without rewriting the file. A stale remembered browsing location alone falls back to root. Writes stage through a pending file and complete before a new snapshot is published. This is not a cross-file transaction: new imports persist membership before adding the Library entry; an interruption can leave an unused membership, which a later new import replaces, but cannot report a successful import in the wrong Folder.

Recursive deletion locks organization, removes each Document's offline narration and Library entry, and removes the Folder subtree last. Library import and deletion use write-before-publish commits. A failed deletion keeps the remaining subtree reachable for retry; already deleted Documents are not promised to return. Membership left by an individually removed Document is unused until a new import explicitly assigns its location. Folder changes do not stamp Library entries or touch the position-sync projection.

The owner selected prototype B (local branch `xujialiu/folder--density-prototype`, commit `7ddfeea`) after simulator review: a shared 84-point row at the default system text size, 40×56 Covers inside a 56-point illustration column, and 44×38 layered blue Folder artwork. The shared row scales with `fontScale`, so Folder/Document types and title lengths cannot choose different row heights. Direct child counts use live Library Document ids rather than all stored memberships, since an individually removed entry can leave an unused membership.

On iOS 27.0, the Folder collision button disabled correctly but `RenameAlert`'s Expo `Alert.Message` rendered no explanation. Both conditional mounting (beta13, screenshots 04/06) and a continuously mounted message slot (beta14, `b14-01-conflict-message.png`) failed; beta14's native alert remained 320×190 with no message accessibility element. The state was reaching JavaScript, as the disabled button proved. A narrow `@expo/ui` patch was tried in commit `9316c1e`: a plain `message` prop on the Alert's observed native props rendered as direct SwiftUI `Text`, preserving the original child-slot fallback for other consumers. It required rebuilding ExpoUI; a JavaScript reload alone could not verify it. The replacement also failed in beta15 after a confirmed successful native rebuild (`build.exitcode` = 0; `SwiftCompile` named both Alert files). The tester reproduced the absent message twice and observed the 61-character refusal string in `AlertProps.message` under LLDB while the button updated. The message was still absent from pixels and accessibility, with the alert remaining 320×190. Changing the prop transport did not repair live message updates; the native patch is not a validated fix. The owner chose submit-time validation instead: blank stays disabled, but a duplicate is submitted and refused by a separate React Native system alert whose entire message is present at opening. Back to editing re-presents the still-mounted SwiftUI editor, preserving its native text binding and JavaScript draft; Cancel ends editing. The ineffective native patch was removed, returning ExpoUI to upstream code.

Picker and external imports share duplicate handling. Cold external arrivals wait for Library loading and navigation readiness, and external arrivals are processed serially so two duplicate alerts cannot replace one another. The add Drawer waits for native dismissal before opening the system picker; it remains mounted for that dismissal callback.

**The move drawer as Files' Move sheet (#151, 2026-10-10).** The owner reported `Move here` changing rows: `MoveContent` rendered the parent row only away from the root, above `Move here`. The owner also reported `Move here` looking pressable at its source, because `DrawerRow` passed `disabled` to its `Pressable` and drew nothing different. Files on an iOS 27.0 (24A434) iPhone 16 Pro simulator, dark, was measured in `notes/NOTES_2026-10-10.md` 13:42. Its header is a round back button, the folder's name, a round `…` and a `Move` capsule at the trailing edge. In the source folder, in the moved folder and in that folder's subfolder, `Move` reads `enabled=False` and is drawn `#505052` with `#ffffff` text; elsewhere it is `#0492fe` with `#f0ffff` text. The moved folder is listed and enterable. A greyed file row's title measured `#5a5a5e` on `#1c1c1e`, which is `rgba(235,235,245,0.3)`, the tertiary label. `MoveContent` became `useMovePage`, which returns the drawer header (`title`, `onBack`, `backLabel`, `action`), the body and `restart()`, because the header belongs to the one `Drawer` that the Document, Folder and selection flows each already render. `restart()` makes each opening start at the entries' own folder: the hook outlives the page in `ReaderActions` and `FolderActions`, and the selection's drawer is always mounted. The pure `moveChoice(tree, moving, from, shown)` in `src/core/folders.ts` decides `canMove` and lists every child folder. The core's own refusals in `moveSelection` and `putFolder` are unchanged. `DrawerAction.prominent` sets the capsule's word in Headline. While the capsule can act, the word is in `accent.onMark` on the plain `colours.button` capsule, as Select all's is. Files fills its Move with the system blue, but the owner chose the word in the App Colour over a filled capsule. A disabled prominent capsule is `colours.inactive` with `colours.inactiveText` and is not faded: `#d6d6d6` and `#505052` with `#ffffff`. Those are Files' disabled Move fills in light and dark, each with white text. The first build drew it as the plain capsule with `INK.text`. In light that is `#ffffff` with `#16161a`, the same as the live back button beside it, so it did not read as grey. The non-prominent capsule (Download's Select all) keeps its 50 % fade. A refusal is `Alert.alert('Could not move', message)` instead of a `DrawerFooter` after the list. A disabled `DrawerRow` draws its line, without the separator, at opacity 0.3. Contents' unreachable rows dropped their own `INK.quiet` so they are not dimmed twice.

**Another entry's actions touched behind an open drawer (#151, 2026-10-10).** The tester found the case on `move-151` (`test/manual-test/library-and-reader/move-drawer.md`). The Library stays touchable up through the Drawer Height (ADR 0066), so a touch on another row's `…` changes the `id` or `document` prop of the `FolderActions` or `ReaderActions` already mounted. Their state survived the change. A Document's move page browsed to `… → Same` stayed there, with `Move` enabled, after another Document's `…` was touched: pressing it would have moved that other Document. Both components now keep the subject they last drew (`shown`). When the prop differs, they reset their page, their alerts' flags and the move page during render, so the same sheet shows the new entry's menu. The sheet is not dismissed and presented again. Keying the components by subject was not used: a remount would unmount one `BottomSheet` and present another through the drawer queue, which had not been measured.
