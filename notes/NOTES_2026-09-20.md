## `caretPositionFromPoint` snaps, so blank space was not blank (2026-09-20 01:00)

Tap-to-seek hit-tests the tapped point to a text node, and the first
implementation trusted the hit-test to say when there was none. It does not.

A `click` dispatched at (2.0, 23.4) — inside the body's own left padding, beside
the first heading, over no text at all — came back with `elementFromPoint` = `BODY`
and `caretPositionFromPoint` = **a text node in the heading**. The reading moved
to that heading's Utterance. Measured again at (1, 1) with the boxes read out:

```
element=HTML  caretType=3  caretText="The First "
ownerBox=33.5/21.4/368.5/59.4   bodyBox=0.0/21.4/402.0/444.9
```

The point is outside the heading's box on both axes and the caret was handed back
anyway. WebKit's caret hit-test answers "the nearest caret position", not "the
caret position at this point", and there is no argument that changes it.

So the tap now has to land **inside the box of the Block it resolved to**. The
Block's box and not the character's: a tap between two lines of a paragraph, or
past the end of a short last line, is inside the paragraph and is an ordinary
"read from about here"; a tap in the margin or on the empty page below the last
paragraph is inside nothing.

The pair, with everything else unchanged:

| tap | before the box check | after |
| --- | --- | --- |
| on text ("A second paragraph…") | Utterance 4 | Utterance 4 |
| at (1, 1), in the margin | Utterance 0 | **unchanged** |

## Fast Refresh does not reload the WebView's program (2026-09-20 01:01)

Cost a wrong conclusion before it was noticed, so it is written down. The
highlighter is a source string handed to the WebView as `injectedJavascript`,
which `react-native-webview` evaluates **at page load** — and the program's first
line is `if (window.__openReaderHighlighter) return true;`, so even a second
injection into a live page does nothing. Editing that file and letting Fast
Refresh re-render the screen therefore changes the string and not the program:
the app keeps running the version the WebView was born with.

The blank-space fix above appeared not to work for exactly this reason. Leaving
the Reader and opening the book again remounts it, which builds a new WebView, and
the change was there. **Any change to `highlighter.ts` needs the book closed and
reopened before it is on the device.**

## The mutation sweep (2026-09-20 01:22)

Twenty-six mutations against the twenty-eight assertions added today, each one
breaking the thing an assertion guards, watching it fail and putting it back. All
but one fail, and the survivor is worth recording because it is not a gap:

**`firstUtteranceOfSection` reading `spans[0]` instead of `spans.at(-1)` is
unobservable.** The repair layer refuses to weld two Blocks from different
sections (`rejoin.ts:217`, `if (a.section !== b.section) return false`), so every
span of an Utterance carries the same `sectionIndex` and the two spellings cannot
disagree. The choice is documentation rather than behaviour, and no test can be
written for it that is not a restatement.

Two mutations survived at first and were real gaps in the assertions, now closed:

- **A half-open span end was indistinguishable in English.** `offset <= span.end`
  passed every assertion, because `sentencex` trims the space between two English
  sentences and leaves a one-character gap between their spans. The two spellings
  differ only where spans are **adjacent**, which is every sentence boundary in
  Chinese: 「第一句。第二句。」 gives spans [0, 4) and [4, 8), and offset 4 belongs
  to the second sentence under one rule and to the first under the other.
- **`NaN` falls out of the comparisons by itself.** The guard on a non-finite
  offset was tested with `NaN`, which every comparison rejects anyway. `Infinity`
  is the value it actually catches: every span ends at or before it, so without the
  guard a tap at `Infinity` answers with the last Utterance of the Block rather
  than with nothing.

## The blank open: a resize with no location destroys the page (2026-09-20 01:51)

Diagnosed, reproduced on demand, fixed, and the fix shown to stop it.

**The mechanism, read out of the bundled epub.js.** The stage's resize observer
calls the view manager's `resize`, which calls `this.clear()` whenever the size
really changed, destroying every view. The only thing that rebuilds them is the
rendition's own handler:

```js
onResized(size, cfi) {
  this.emit(RENDITION.RESIZED, { width: size.width, height: size.height }, cfi);
  this.location && this.location.start && this.display(cfi || this.location.start.cfi);
}
```

`this.location` is set by `reportLocation`, which first runs when the opening
`display()` resolves. A resize landing before that re-displays nothing.

**Reproduced, both directions, on the two-section fixture.** A forced resize of one
pixel, with everything else unchanged:

| | inside the `resized` handler | 700 ms later |
| --- | --- | --- |
| `rendition.location` left alone | views 0, location yes | **views 2, children 2** |
| `rendition.location` cleared first | views 0, location NO | **views 0, children 0** |

The second is the blank open exactly as the 20:44 and 22:55 entries of 2026-09-19
describe it: zero views, an empty container, and the player still saying "18
Utterances ready" because the Blocks had been reported before the page went. The
screenshot of that forced blank is indistinguishable from the one taken of the real
thing yesterday.

**The trigger, caught once in the wild.** Opening 仙逆 laid the document element out
**twice**:

```
17:55:51.141  LAYOUT document 402x874
17:55:52.775  LAYOUT document 402x758
```

1.6 seconds apart — the navigation header's height arriving. 874 is the full screen;
758 is what is left under the header. The book's opening `display()` on 2,077
sections has often not resolved inside 1.6 s and the fixture's always has, which is
the shape of "two opens in three on the big book, one in four on the small one".

It is a race and not a rule: seven later opens of the same book (four from a cold
launch, three from a return to the Library) laid out **once**, at 402×758, and never
resized at all.

**Four other callers of `clear()` exist and none of them fits.** `destroy` is
teardown; `next` and `prev` are only reached by a page turn; `display` clears
*before* it renders, so a failing one cannot produce the recorded symptom of
sections having rendered and reported their Blocks first. `resize` is the only
caller that clears something that was already there.

**The fix**, in `highlighter.ts`: listen for `resized` and re-display **only when
epub.js has declined to** — when there is no `location.start`. The target is the
lowest spine item the last sweep saw on the page, because by the time the handler
runs `clear()` has destroyed the views and scrolled the container to zero, and there
is nothing left to read a finer position off.

**The same forced resize with the fix in place:**

| book | at the resize | 700 ms later |
| --- | --- | --- |
| `reading-aloud.epub` | views 0, location NO | **views 2, children 2** |
| 仙逆 | views 0, location NO | **views 3, children 3** |

仙逆 came back at 第491章, one section above where it had been — the top of the
lowest section that was on the page, which is the documented trade.

**How long each run was.** None of this played any audio at all: it is a rendering
defect and a reading would only have added clip fetches to the log. The four cold
launches took about 20 s each because a 34 MB book needs that long to open, and four
was chosen to be more than the three the 20:44 entry sampled. Everything else was
single forced resizes, seconds apart.

**What is not claimed.** The wild blank was never caught with a watcher installed —
it did not happen in the eleven opens run today, with or without the fix. So this is
a mechanism that reproduces the entire recorded symptom set and that no other caller
of `clear()` can produce, not a recording of the original failure. Seven clean opens
against a recorded two-in-three failure rate is suggestive and nothing more; the
before/after on the forced resize is the evidence.
