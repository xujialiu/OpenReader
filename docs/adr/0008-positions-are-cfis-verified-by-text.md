# A reading position is a CFI checked against a text anchor

_Measured and refined by [ADR 0031](0031-positions-cross-products-by-document-id.md):
the round trip was run on 2026-09-21, the locator is an **element** CFI with no
text step and no assertions, and the retreat named at the end was not needed._

A reading position records both a native locator for its format — for EPUB, the
CFI the desktop plugin already stores — and a text anchor: a quotation of the
utterance with enough surrounding context to find it again. Resolving a position
uses the locator first, then compares the text actually found against the
anchor, and falls back to searching for the anchor when they disagree.

The product argument is in `docs/design/0008-resuming-where-you-actually-stopped.md`.

## Why not the CFI alone

Two facts make a bare CFI unsafe across products. Zotero's reader resolves CFIs
with its own copy of epub.js rather than upstream, and Zotero's CFI generator
and resolver disagree with each other about text steps — which is why the
desktop plugin never generates a CFI of its own, and instead brute-forces the
adjacent odd text steps until one resolves. A CFI generated by a standard
epub.js on the phone and handed to Zotero is the combination nobody has tested,
and issues #3 and #4 showed that failure mode is not an error but a silent
resolution to the wrong node. A bookmark that quietly lands three paragraphs away
is worse than no bookmark.

## Why not count utterances instead

Because the two products segment differently — this app uses upstream
`sentencex`, Zotero uses SDT (ADR 0006) — so "the 214th utterance" means a
different place on each side.

## Why this is cheap here specifically

It generalises a rule the desktop plugin already relies on: its highlight code
accepts a candidate CFI only when the text it displays matches the segment text,
so text is already the arbiter of whether a locator is correct. And the
machinery for matching text that does not match exactly already exists —
`core/align.ts` is a longest-common-subsequence aligner written for the same
class of problem, when a provider reports words that differ from the ones it was
given.

## Matching a quotation, not a substring or an arbitrary early copy

A character hit must respect the quotation's edges (#282). `7` inside `1907`,
`Chapter 1` inside `Chapter 10`, and a Han heading inside a longer Han word are
not the same quotation. Adjacent letters, marks or numbers require the stored
context to attest that adjacency; ASCII word boundaries alone cannot serve
scripts without spaces. Token-exact matching can still find a reflowed valid
quotation elsewhere, but approximate alignment cannot rescue a rejected
substring. An unpunctuated whole-Block heading must match all its words, not
lose its number to the aligner's partial-match allowance. Original-text offsets
and NFC/NFD matching are preserved.

Every occurrence within a Block is eligible for context ranking (#283), not
only the first 64. In the real splitter/cursor regression, the 65th `Yes.`
previously resumed at the first while the 64th resumed correctly. Raising the
cap would only move the failure; the matcher now retains a best candidate and
tie flag without sorting. Context scoring binary-searches the token edges and
compares only the stored context instead of scanning all tokens for each hit.
The tests include 10,000 occurrences without changing the sentence splitter.

A Locator names a Block, not a particular copy of a sentence within it. Tied
copies are therefore unresolved even when the Locator succeeds; fallback
search likewise carries ambiguity within its winning Block, not only ties
between Blocks. The existing ambiguous-resume notice is used. The cost is an
explicit refusal when the stored 32-code-unit context cannot distinguish
copies, rather than a silent jump presented as a verified sentence. No shared
Reading Position field, locator dialect or context length changes.

## Consequences

Text anchors must be Unicode-normalised on both the storing and the matching
side. Zotero normalises EPUB text to NFC, and an exact comparison against a
document that happens to be NFD fails silently — the plugin has already been
bitten by this once.

If round-trip testing shows CFIs do not survive between the two products even
with verification, the fallback is that EPUB positions sync only between this
app's own devices while settings continue to sync with the desktop. That is a
retreat, not the starting design.
