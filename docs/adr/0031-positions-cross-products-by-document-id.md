# Positions cross products in one file keyed by Document Id

_The product argument — who this is for and what it costs — is
`docs/design/0031-your-place-follows-you-to-the-desktop-and-back.md`. The
contract itself is the desktop plugin's `docs/spec/SYNC-FORMAT.md`, which both
products implement; this ADR records why it has the shape it has and what was
measured to get there._

ADR 0003 chose the owner's WebDAV folder and asked the desktop plugin, in its
issue #126, for a `zotero-tts-documents.json` mapping Zotero's `{lib, key}` to
a content id. That request is withdrawn. Instead both products write **one new
file, `xujialiu-positions.json`**, keyed by the Document Id of ADR 0004, whose
items are Reading Positions in this app's own shape — a Locator, a Text Anchor
and a Stamp — and the plugin's own `zotero-tts-positions.json` is left exactly
as it is.

## Why a second positions file rather than the plugin's

The plugin's file cannot be the crossing point, for two reasons each of which
is sufficient:

- It is serialised canonically to exactly four fields, `{lib, key, pos, ts}`,
  and an older build strips anything else on its next merge-and-upload
  (ADR 0003). So it can carry no Document Id and, worse, **no Text Anchor** —
  and ADR 0008 exists because a bare locator crossing between the two
  products fails silently, by landing on the wrong node.
- `pos` is Zotero's own dialect: for EPUB a range CFI with text steps and
  character offsets, generated by a generator that disagrees with Zotero's own
  resolver about text steps (plugin issues #3, #4). Writing one from this side
  would be the untested combination, with no anchor to catch it.

A mapping file, as #126 asked, would have let the phone *read* the plugin's
file by joining on the id. It would not have let the phone write for the
desktop, and it would have left a book the owner put on the phone by hand —
which is in no Zotero library — with no way to keep its place between two
phones. A file keyed by Document Id needs no mapping at all: the desktop keeps
`{lib, key} → id` in its own database, where `lib` is correct, and nothing in
the folder ever mentions Zotero's coordinates.

## The name

`xujialiu-positions.json`. Three names were weighed. `positions.json` was
chosen first and withdrawn: the plugin heals a malformed file by overwriting
it, and with a generic name that rule would overwrite another program's file in
a shared WebDAV folder. `openreader-positions.json` was withdrawn because the
plugin retires its own file in 2.0 and this one then serves desktop-to-desktop
sync for owners who never installed this app; the name would say who it was for
rather than what it holds. The author's name marks the file as a contract
between the owner's products, as against the plugin's private `zotero-tts-*`
files, and the naming rule is now in the spec: `zotero-tts-*` may change by the
plugin's own policy, `xujialiu-*` changes only through the spec.

## The item, and what is fixed forever within version 1

```json
{"id":"sha256:…","format":"epub","publicationId":null,"locator":"epubcfi(/6/34!/4/2/4/2/4)","anchor":{"exact":"…","prefix":"","suffix":""},"stamp":{"at":1758470000000,"device":"iPhone-3f9a2c1b"}}
```

Six fields and no more, because ADR 0003's rule is that nothing is added
within a version. Two of them are here for a future that has not arrived:
`publicationId` is reserved for `dc:identifier`, written `null` by both sides
and never a key; `format` is `epub` today and `pdf` / `snapshot` are reserved,
with their id rules and locator dialects undefined. The second is what lets the
plugin retire its own file one day without a version bump: adding a format is
a new value in an existing field, provided every reader **carries through**
items whose format it does not implement. That carry-through rule is the one
place this file's parser deliberately differs from `parseLibrary`, which drops
and reports an unknown format because nothing here could act on it — a rule
that is right for a file only this app writes and would erase the desktop's
PDF positions on the phone's first upload here. A carried item is written in the
canonical form like any other, with its values as parsed. Its `anchor` and
`stamp` keep only the keys the spec lists, in its order (#59, Zotero-TTS #139).
Until then this side kept them as parsed, key order and unknown keys included,
while the plugin wrote them canonically. So one hand-edited item came out of the
two products two ways, and the file changed once more after the phone had
written it.

No title, no voice, no `lib`, no `key`. A title is a display cache the plugin
has no use for; a Voice belongs to a Provider and a credential that differ
per device (ADR 0010); the Zotero coordinates mean nothing off the desktop.

## The locator is an element CFI, and the measurement that allows it

ADR 0008 named the CFI round trip the one thing that had to be tested before a
position was ever stored for the other product. It was measured on 2026-09-21
(`notes/NOTES_2026-09-21.md`, 17:11) against the running Zotero 10.0.3 and the
epub.js this app actually embeds — `@epubjs-react-native/core@1.4.8` carries
its own build as a string, fingerprint-identical to npm `epubjs@0.3.93`, and
writes it to the document directory on every mount; no CDN is involved. Four
books, every section, 132,467 Blocks:

- An element CFI minted by `cfiFromNode(blockElement)` named the **same
  block** in Zotero's Read Aloud mapper and in its DOM resolver for
  **121,376 of 121,376** paragraph and heading Blocks of the two `.xhtml` books
  (仙逆 and an El Akkad novel), nested `div`s, `blockquote`s and inline markup
  included; the spine step `/6/N` agreed on all 2,096 sections. The reverse
  held for 125,533 of 125,533 element-anchored Zotero paths.
- Zotero's own **text-node** paths resolve correctly in upstream epub.js for
  **81 of 430**: Zotero numbers text steps by the spec (`1 + 2 × elements
  before`) and upstream counts text nodes. So the locator carries no text
  step, no offset and no range, and the plugin writes the SDT block's own
  element path rather than truncating a range CFI.
- `[id]` assertions that are true resolve identically in Zotero; a wrong one
  makes its DOM resolver answer null while its mapper still resolves. Upstream
  emits them wherever an element has an id, so they are **stripped** before a
  locator is written and the renderer compares Blocks assertion-stripped, so
  that a desktop-written locator finds its Block by string.
- The one seam is not in either CFI implementation. This app hands sections to
  the WebView through `srcdoc`, so they are **parsed as HTML**, while Zotero
  parses every member as XHTML. For `.xhtml` members the trees are identical
  (element counts equal before and after the reparse in all 2,096 sections).
  For `.html` members with self-closing tags — an O'Reilly book's
  `<a data-type="indexterm" id="…"/>` — the HTML parser treats the tag as open,
  and every later sibling in the chapter is one step off: 50 same-path,
  different-text paragraphs, 1,645 of 2,422 CFIs unresolvable, **silently**. A
  `<table>` without `<tbody>` gains a step the same way.
- Zotero splits some Blocks this app treats as one: an `<li>` holding a
  nested list is a container to Zotero's mapper (null → segment 0), and the
  `<dd>` paragraphs of a `<dl>` are absent from its Read Aloud data altogether
  (processor v2), so a position inside one lands on the `<dt>` terms.

The conclusion is the one ADR 0008 hoped for and could not assume: an element
CFI is the half of the dialect both sides agree on, and the **Text Anchor is
the arbiter** of whether it landed. Neither side ever starts reading from a
bare locator. The plugin resolves the anchor itself inside the open reader —
block by locator, then `exact` in the block's NFC text by characters, tokens
and the aligner both products carry as `core/align.ts`, then every block with
`prefix`/`suffix` ranking, a tie refused — and only then builds a native
position for that sentence. On this side `resolveReadingPosition` already does
exactly that over the rendered Blocks (ADR 0008, ADR 0019).

## A Reading Position carries its own Stamp

The Library entry's `stamp` moves on `opened`, `rename` and `retitled` as well
as on `reached`: it says when the owner last touched the book, which is what
orders the shelf. Used as the position's stamp in a merge it picks the wrong
winner in the most ordinary case — the desktop reads to chapter 200 on Monday
night, the owner opens the book on the phone on Tuesday morning without
reading, the entry stamp is now Tuesday, and the phone's chapter 100 beats the
desktop's chapter 200 on every device. So `ReadingPosition` gains a `stamp`
that moves only when speech stops somewhere new, written as
`max(now, previous.at + 1)` — the plugin's own rule, so a device with a slow
clock still outranks the item it adopted the moment it reads on. The Library
file becomes version 2; a version-1 position with no stamp reads as the oldest
possible, which is what `parseStamp` already does for an entry, and is what
"no migration before release" means here: the owner's chapter-100 place loses
its first merge against any remote copy rather than winning it by accident of
when it was parsed. The entry stamp goes on ordering the shelf, and moves up
to an adopted position's stamp when that is newer, so a book read yesterday on
the desktop rises above one opened last week.

`stamp.device` is attribution only; the merge compares `at` alone. The plugin
writes its machine id, which exists for the one-file-per-machine settings
backup. This app has no such need and therefore no setting: philosophy rule 6
removes a field that changes nothing the owner can see. `this-device` now
holds `iPhone-` or `iPad-` and eight random base-36 characters, made once, so
two phones of one model still differ and a person reading the file can tell
them apart. Not `identifierForVendor`: an opaque UUID is less readable and is
a linkable identifier for no benefit.

## Merge, lifecycle and the rules copied from the plugin

Union by `id`, greater `stamp.at` wins, equal keeps the reader's own item, so
merging a file into itself is a no-op. **Nothing removes an item**: a deleted
Zotero attachment, a book taken off the shelf, a phone that is gone — the
document may exist elsewhere and its place is the point, and an item is a few
hundred bytes. A document with no position contributes nothing and cannot beat
an item that has one. Every sync is download → merge → conditional upload with
no ETag, one in flight and one queued (`core/single-flight.ts`), one report per
retry window; a lost concurrent write is healed by the loser's next sync
because the local store is the truth. A `version` above 1 leaves the file
alone and says so; a malformed file is treated as absent and overwritten,
which the specific name makes safe. All of it is the plugin's
`position-transport.ts` shape, and `core/webdav.ts` comes across as a copy by
ADR 0013's rule, with its tests.

## When the phone syncs, and what it does with what arrives

Launch, return to foreground, opening a book, adding a book, pause or stop,
leaving the reader, entering the background. Never on a timer while reading.
Pause syncs **at once** rather than after a quiet period: a phone paused from
the lock screen may be suspended within seconds, and the plugin's ten quiet
seconds are a desktop's luxury.

The plugin's moments were the reason the two new ones exist on both sides. It
synced at startup, reader open, tab close and shutdown, so a desktop paused
with its tab open never uploaded, and Shift+Space never downloaded first — the
two moments the whole cross-device story turns on. It now syncs ten quiet
seconds after Read Aloud pauses or the player closes, and pulls for at most two
seconds before a resume.

What arrives is adopted when its stamp beats the entry's position stamp, or
the entry has none. In the reader, ADR 0019's rule stood in the way: "anything
else deciding where to read ends the bookmark's claim", so a place arriving
after the owner had pressed Play once would have waited for the next open, and
the owner's own scenario — pause on the phone, read on the desktop, come back
and press Play — would have resumed at the phone's stale place. The rule is
now: **while paused, the newest place wins.** A newer adopted position moves
the cursor and the page to that sentence through the resume machinery, with no
sentence of explanation (design 0026 removed successful-resume messages; the
moved highlight is the signal); pressing Play while paused first syncs for at
most two seconds and resumes from the newest place. A sync slower than that
plays from the local place and moves nothing while the reading plays. While
playing nothing moves. What that run adopts is kept by the Reading and
settled when the reading stops (#105, below). Before the owner has acted, an
arriving place still takes over the resume, as ADR 0019 allows.

The rule used to be that a late adoption is not applied at all, "because ten
seconds into the reading the phone's own stamp is the newest anyway". That
holds only once the phone has written a place. It had not written one when the
owner paused before speech left the sentence the reading resumed at, because
`readingPosition()` answers null there (`resumedAtRef`) and nothing is
stamped. The Library then held the other device's place while the Reading
stayed on the older sentence. The next Play's sync found the Library equal to
the file and adopted nothing, and Play offers only what its own run adopted.
So the older sentence was read again, and its continuation was stamped above
the newer place and uploaded (`notes/NOTES_2026-09-30.md`, 19:13: cursor 0
instead of 2, `Phone old continuation.` on the server). Now `resumeAt` keeps a
place it declines while playing. The effect that sees the reading stop, by a
pause, the lock screen, the headphones or the end of the book, takes that place
if `readingPosition()` is still null. Otherwise it lets the place go: speech
reached another sentence, or the owner tapped or skipped, and the pause writes
that sentence above the kept place. A Contents row chosen while playing lets
it go at once, before its chapter reports and moves the cursor. And a place
the cursor is already on is taken without a seek. Otherwise Play taking an
adoption, followed by the arrival effect passing the same place on after
playback starts, would re-seek the sentence at the next pause.

Pressing Play did not do that until #54 (2026-09-24), for two reasons measured
at the unit seams (`notes/NOTES_2026-09-24.md`, 01:43), either enough alone.
The adopted place usually names a section the phone has not rendered, because
reading forward on the desktop goes past what the phone has laid out, and
`play()` opened with ADR 0019's claim rule, which gave up a place still pending:
the engine loaded at the phone's own sentence, under a note that blamed "the
place this book was left at". Play now waits for that section (ADR 0019, the
Play bullet). And `flush` resolved with a variable the transport shared between
runs, while `createSingleFlight` starts a queued run inside the finished run's
own cleanup, before the awaiting caller resumes; that run's first line cleared
the variable. So whenever a poke had queued a run meanwhile — the app coming to
the front as Control Centre closes, or as the phone is unlocked after a
lock-screen Play — `flush('play')` answered null, which Play reads as "sync is
off", and the place its own run had just adopted was skipped. `flush` now
resolves with the outcome its own run returns, carried on that run's promise.
Both ended the same way: the next Clip boundary wrote the phone's older sentence
stamped `max(now, adopted.at + 1)`, the next pause uploaded it, and the
desktop's next resume took it, so the place reached on the desktop was lost on
both devices. The same could happen without Play, so while a place is pending
`readingPosition()` answers null: no pause, renumbering or exit writes the older
sentence over it.

## The switch, and where the password lives

There is a switch, and the reason it is not a switch that does nothing is what
it does when turned on: it runs the connection check the plugin's pane runs
(a PROPFIND on the folder), passes on success and on a 404 folder — the
credentials were accepted and the folder is created on the first upload — and
then **locks** the address, the username and the password until it is turned
off again. Off, the three fields are editable; a failed check flips the switch
back off with the reason on the one status line. The address, the username and
the switch live in `settings.json`; the password is a Keychain entry kind of
its own beside the provider keys, on ADR 0002's three grounds: it is a bearer
credential, it is needed with the screen locked, and its alternative home is
the very folder it opens.

## What is given up, and what stays open

- A file in the owner's WebDAV folder named after a person. One line in the
  plugin's release notes says what it is.
- Every device writes a quotation of the sentence it stopped on into that
  file, which a CFI never revealed. The server is the owner's own.
- A `.html` EPUB with self-closing tags resumes through the anchor search
  rather than the locator, every time, on this side; the search covers the
  rendered sections only, which is safe because the spine step agreed on every
  section measured.
- `publicationId` is written `null` by both sides; the secondary match ADR 0004
  wants is still not built.
- PDF and snapshot positions stay in the plugin's own file; the plugin retires
  that file in 2.0 only once their id rules and dialects are in the spec. The
  owner reads papers on the desktop and novels on the phone, and said so.
- `<style>`, `<link>` or `<title>` inside `<body>` was in no book measured; the
  sanitiser shift that the static reading predicted remains a prediction.
