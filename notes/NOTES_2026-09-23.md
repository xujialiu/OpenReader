# OpenReader — engineering log, 2026-09-23

## npm will not search downward for a peer it has already locked (2026-09-23 02:44)

npm 10.9.8, node v22.23.2, `main` at 0c2674b, no `node_modules`, no `.npmrc` in the repository or in `$HOME`, `npm config get legacy-peer-deps` = `false`.

`npm ci --dry-run --ignore-scripts` exits 1 in 0.64 s with `Conflicting peer dependency: react@19.3.0`. That is the whole signal for #42 and it needs no network beyond the registry metadata npm already has.

Copying `package.json` and `package-lock.json` into an empty directory and running **`npm install --package-lock-only --ignore-scripts` with no flags fails the same way**. npm keeps the `react-dom@19.3.0` the lockfile already names and reports the conflict; it does not try 19.2.x to find one whose peer `react@19.2.3` satisfies. So a lockfile in this state cannot be rewritten out of it — the version has to be named.

Naming it with `"overrides": { "react-dom": "$react" }` and re-running the same command changes exactly two nodes:

| | before | after |
| --- | --- | --- |
| `node_modules/react-dom` | 19.3.0 | 19.2.3 |
| `node_modules/react-dom/node_modules/scheduler` | 0.28.0 | gone — 19.2.3 wants `^0.27.0` and shares the root 0.27.0 |

17 changed lines in `package-lock.json`, nothing else in the tree moves, and `npm ci --dry-run` then exits 0.

A caret would not have done: `react-dom@19.2.8` is published and peers with `react@^19.2.8`, which `react@19.2.3` does not satisfy, so `^19.2.3` resolves back into a conflict. `$react` resolves to the pinned spec exactly.

## The speed stepper inside the system popover: taps, holds, and taps that pass through (2026-09-23 20:30)

iPhone 17 simulator, iOS 27.0, `@expo/ui` 57.0.19's `Popover` (its `PopoverView.swift` applies `.presentationCompactAdaptation(.popover)`), a throwaway branch of `player.tsx`: `Host` 58 × 44 → `Popover` (controlled, `attachmentAnchor="top"`, `arrowEdge="bottom"`), trigger `RNHostView` without `matchContents` holding the speed label's `Pressable` at `flex: 1`, content `RNHostView matchContents` → padded `View` → the existing `Speed` with 36 pt buttons. The installed Debug app already carried `PopoverView` and `RNHostView`'s touch handler; a JavaScript reload was enough. Evidence in the session scratchpad (`spike/`).

- It opens as a bubble above the label, not as a sheet: the buttons end at y 768.3, the label's top is at 797.7. The bubble was 260 × 68.7 pt, its content's size, with a 13 pt arrow. A full-screen `PopoverDismissRegion` ("dismiss popup") is in the tree. In the dark the bubble turns dark.
- One tap on Faster: 1.50 → 1.55, and Slower back to 1.50; the label ("Playback speed, 1.55 times") and the bubble's number agreed each time.
- A 2.0 s `press(forDuration:)` on Faster: 1.50 → 2.55, 21 steps; on Slower 2.55 → 1.50. Unchanged 0.3 s and 1.3 s after release, so `onPressOut` was not missed. The drawer, as a control, gave 21 steps each way too.
- The bubble is the system's glass: what is behind it shows through, distorted (the player's amber note read as a smear in the light, mirrored along its top edge in the dark).
- A tap outside always closed it (6 of 6 dismissals fired `onIsPresentedChange` once each), and what the tap landed on decided what else happened:

| Where the outside tap landed | What happened |
| --- | --- |
| Contents button (3 times) | the bubble closed **and the contents opened** |
| the voice line (once) | the bubble closed **and the voice sheet opened** |
| the page's text (3 times) | the bubble closed; highlight and position unchanged |
| the same page tap with no bubble (control) | the sentence was highlighted, the position moved |
| the native back button (once) | the bubble closed |
| the speed label itself (once) | the bubble closed |

So a React Native `Pressable` under the tap receives it as well as the popover's dismissal region; the page's WebView and the native header do not. Play, Previous and Next were not tapped (nothing was to play), and are `Pressable`s like Contents.
