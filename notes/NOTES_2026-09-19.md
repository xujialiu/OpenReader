## Hermes: what the engine in React Native 0.86 actually has (2026-09-19 12:21)

Measured, not inferred. Hermes **250829098.0.17** — the engine RN 0.86.3 bundles —
debug build, iOS 27.0 simulator. Measured by `src/spike/hermes-support.ts`,
rendered on the app's first screen; that directory went when items 1 and 2 were
struck, so this note is the record rather than a pointer to one.

| Feature | Result | Why it was in doubt |
|---|---|---|
| `String.prototype.normalize('NFKC')` | **yes** | Has crashed on Hermes historically; absent from recent release notes. Verified against fullwidth Latin, a circled digit, an fi ligature, a CJK compatibility square and a no-break space. |
| `TextDecoder` | **yes** | Release notes of 2026-06-05 said it now ships with the engine; an older issue said otherwise. It exists, reports `utf-8`, decodes 3- and 4-byte sequences, and keeps state across a chunk boundary with `{stream: true}`. |
| `normalize('NFC')` / `('NFD')` | yes | Needed by the text anchors of ADR 0008, since EPUB text may arrive either way. |
| `\p{L}`, `\p{Script=Han}` | yes | Load-bearing in the word aligner being ported. |
| **`Intl.Segmenter`** | **NO** — `Intl.Segmenter is not a function` | Hermes ships a cut-down `Intl`. |

**Both open questions from ADR 0001 resolve favourably.** Nothing in the ported
aligner needs a polyfill or a JavaScriptCore decision.

The new finding is the last row, and it changes two things. `unicode-segmenter`'s
`intl-polyfill` is **required**, not a hedge — and item 7 of the verification list
loses half its meaning: there is no platform `Intl.Segmenter` whose sentence
quality could be judged. What gets judged is the polyfill's.

## More globals, measured the same way (2026-09-19 13:20)

A second pass over the same screen, while porting the provider layer, because
the survey of the plugin's code claimed React Native ships no `TextDecoder` and
no `TextEncoder`, and because the base64 path the providers use rests on `atob`.
Nothing in `react-native/Libraries/` defines any of them, so reading was not
going to answer it.

| Global | Present |
|---|---|
| `atob` / `btoa` | yes |
| `TextDecoder` / `TextEncoder` | yes |
| `AbortController` | yes |
| `WebSocket` | yes |

`atob` is **binary-safe**: `atob('//7//w==')` gives char codes `255,254,255,255`,
so the byte-for-byte loop in `providers/audio.ts` is sound and no base64 library
is needed. `TextEncoder` matters later — `core/webdav.ts` builds its Basic auth
header with one (ADR 0003).

They come from the engine, not from React Native's JavaScript: no file under
`react-native/Libraries/` or `@react-native/js-polyfills` mentions any of them.
That is why they were measured rather than looked up, and why the answer belongs
to this Hermes rather than to React Native in general.

## The provider contract does not yet return PCM (2026-09-19 12:52)

ADR 0013 says a synthesis result is "raw PCM + sample rate, not a `Blob`". The
code it is a decision *about* does not do that yet. `src/core/providers/types.ts`
in Zotero-TTS declares `SynthesisResult = { audio: Blob; timestamps?: Timestamp[];
note?: string }`, and `Blob` is constructed at **19 sites** across the providers
plus `core/wav.ts` and `core/silence.ts`. Sample rate exists only as
provider-internal constants (`PCM_SAMPLE_RATE = 24_000` in `speechify.ts`, the
`audio-24khz-…` format string in `azure.ts`) and as an argument to `pcm16ToWav`.

So ADR 0013's "copied, ~95% portable" is accurate about *Zotero* coupling — the
whole of it is two unused functions in `azure.ts:43-53` that the provider never
calls — and understates the port. The real work is the contract change, which
every provider touches, and which is mandatory rather than cosmetic: React
Native's `Blob` constructor rejects a `Uint8Array` outright.

Two things ADR 0013 lists as porting risks are **already settled** by the Hermes
measurement above and need not be re-spiked: `align.ts`'s `normalize('NFKC')`
and the `\p{Script=Han}` family of escapes both work.

Three couplings found that the ADR does not mention:

- `factory.ts:12` imports `./system` as a **value**, so porting it drags in 1,190
  lines of PowerShell and `osascript` plumbing. The `'system'` case and
  `ProviderDeps.system` have to be cut (ADR 0014 puts OS voices in a native
  module anyway).
- `factory.ts:1` is `import type { Settings } from '../settings'`, and
  `settings.ts:492` holds `createZoteroPrefs()`. Type-only today, so it erases —
  but one change to a value import pulls the Zotero global into the providers
  directory, and the lint boundary of ADR 0013 does not watch that path.
- `memory-cache.ts:1` imports a type *upward* from `../read-aloud/`. It has to be
  re-homed or the inward-pointing dependency story leaks on arrival.

One correction to ADR 0013's reasoning, which does not change its conclusion: it
says "the provider tests reach for `core/wav` and `core/settings`". They do not —
every one of the 20 test files imports only `vitest` and files under
`src/core/providers/`. The couplings are in the source (`speechify.ts` → `../wav`),
not the tests. The rule still has to cover all of `src/core/`; the stated reason
for it is wrong.

## Keychain accessibility is sticky, and entries outlive the app (2026-09-19 12:59)

Read out of `expo-secure-store` 57.0.4's own Swift, not its documentation.

`set()` puts `kSecAttrAccessible` on the `SecItemAdd`. On `errSecDuplicateItem`
it falls through to `update()`, whose update dictionary is
`[kSecValueData: valueData]` and nothing else. So accessibility is fixed at the
moment an entry is first created and **no later save changes it** — and
`deleteValueWithKeyAsync` ignores the status of all three `SecItemDelete` calls
it makes, so deleting an absent entry reports success.

Combined with ADR 0002's own note that Keychain entries survive uninstall, this
is a trap with a long fuse: anyone who ever ran a build that saved a key at the
default `WHEN_UNLOCKED` keeps that entry, and every later save at
`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` silently leaves it where it was. The
symptom arrives much later and somewhere else — playback stops when the screen
locks, which looks like an audio-session problem.

`src/keys/store.ts` therefore deletes before adding, which makes "save the key
again" the repair. The price is real and is reported rather than hidden: a write
that fails after a successful delete leaves no key at all.

## The segmenter: `sentencex` on npm is two different packages (2026-09-19 13:33)

Measured while building `src/core/segmenter/`, and it decided the pin. Read from
the installed files; none of it is in the package's README.

**1.x is a native Rust addon and cannot run in the app.** `sentencex@1.0.31`'s
`index.cjs` is
`module.exports = require('sentencex-' + process.platform + '-' + process.arch)`,
and `node_modules/sentencex-darwin-arm64/index.node` is a 3.4 MB `Mach-O 64-bit
dynamically linked shared library arm64`. `index.mjs` imports `node:module` and
`node:url` to do the same. Five binaries are published — darwin x64/arm64, linux
x64/arm64, win32 x64 — and there is no mobile one. Hermes cannot load a native
addon and Metro cannot bundle a `.node`, so the 1.x line runs under vitest on a
developer's macOS and nowhere a book is read. `0.4.2` is the last 0.x and the
last pure JavaScript release; 1.0.0 is the cutover.

**So the pin is `^0.4.2`**, and the caret is bounded by the major. ADR 0006's
decision — upstream `sentencex` rather than a copy of SDT — is untouched by which
release is loadable, which is why the answer was a pin and not a port.

Three things about 0.4.2 that cost work:

- **No types, and a default-only export.** `dist/esm/index.js` ends
  `export{et as default}`; `dist/cjs/index.cjs` ends `return rt`. There is no
  named `segment`, so `import { segment } from 'sentencex'` is `undefined` at
  runtime, and there is no `.d.ts`, so it is `TS7016` at build.
  `src/core/segmenter/sentencex-module.d.ts` is the shape written out by hand,
  and `test/core/segmenter/offsets.test.ts` asserts the runtime shape so a
  version bump fails a test rather than type-checking quietly. That file is
  **not** named `sentencex.d.ts`: TypeScript takes a `.d.ts` beside a `.ts` of
  the same basename for that file's own declaration output and leaves it out of
  the program, silently, with the TS7016 still reported.
- **Its pieces do not concatenate back to the input.** The whitespace between
  sentences is dropped: `segment('en', 'One. Two.').join('')` is `'One.Two.'`.
  1.0.31 round-tripped exactly. `src/core/segmenter/sentences.ts` never relied on
  concatenation — it locates each piece from a forward-only cursor and requires
  the gap it skips to be whitespace — so this cost nothing but the tests that had
  asserted the stronger property.
- **29 languages, not ~244.** `am ar bg bn ca da de el en es fi fr gu hi hy ja kk
  kn ml mr my nl or pa pl pt ru sk ta te`. Everything else falls back through the
  package's own `fallbacks.json` and finally to English — `ro` and `zh` both do.
  The English terminator list includes `。` and its relatives, so a Chinese
  paragraph still splits; what does not is quoted speech, below.

### What the pin costs, measured case by case

0.4.2 against 1.0.31 on the plugin's fixtures (`test/fixtures/`, ADR 0006). Each
row is a test in `test/core/segmenter/fixtures.test.ts`, asserting what happens
rather than what should.

Worse on 0.4.2:

| Text | 1.0.31 | 0.4.2 |
|---|---|---|
| `He lives in the U.S. The next sentence starts here.` | two sentences | one |
| `The meeting is at 5 p.m. Bring the report.` | two sentences | one |
| `covers 3 mm. Then it ends.` | two sentences | one |
| `他说：“我不知道。”然后离开了。` (`zh`) | two | one |
| `<The next sentence keeps its words and punctuation.>` | one utterance | `…punctuation.` + `>` |

The first three are one mechanism: on 1.0.31 a known sentence starter overrode
the abbreviation list, and on 0.4.2 an abbreviation blocks the break
unconditionally. (`mm` and `m` are in the English list; `cm` and `kg` are not.)
The Chinese row is the English fallback doing the wrong thing well: the English
quote-pair rule protects everything between `“` and `”` from being cut, which is
right for English and wrong where the `。` inside the quotation ends the
sentence. An unquoted Chinese pair still splits. The bracket row is a bug in
0.4.2's `Language.parensRegex`, which lists `<` as an opening character and does
not list `>` as a closing one, so an angle group is never protected; the lone `>`
that results is not Speakable, so it becomes silence rather than being read
aloud, and the damage is a pause.

Better on 0.4.2: `Really?! I had no idea. Amazing.` is three sentences, where
1.0.31 read through the `?!`.

Unchanged and still wrong on both: `See Sec. 4 and Eq. 12.` breaks after `Eq.`;
`Vol. 3, no. 2, pp. 44-51.` breaks after `Vol.`; `1. Introduction 2. Methods` cuts
after each number instead of before it; `M. Dupont est ici.` breaks after `M.`
when the language is `fr` and does not when it is `en` — which is the argument
against assuming a per-language rule set is per-language *better*.

Unchanged and right on both: `Dr.`, `Mr.`/`Mrs.`, `Fig. 3`, `et al.`, `e.g.`,
initials (`J. R. R. Tolkien`), `$3.50`, decimals, thousands separators,
percentages, a trailing `[1]`, an ellipsis mid-sentence, a line break inside a
sentence, the Greek question mark under `el` and not under `en`, Dutch `bv.`
under `nl`, all three Romanian normalisations of the diacritics fixture, the CJK
fixture's three sentences at 16/24/11, and the Japanese full stop.

**notes/NOTES.md item 7 is not closed by any of this.** 107 tests establish where
the floor is. Nothing here has been read against a real book, and the 29-language
fallback is a second reason the item stays open rather than the first.

## The `unicode-segmenter` polyfill has no word segmenter, and Node hides it (2026-09-19 13:35)

`unicode-segmenter/intl-polyfill` installs `Intl.Segmenter` where the engine has
none, and the adapter behind it implements **`granularity: 'grapheme'` only**:
`'word'` and `'sentence'` each `throw new TypeError` (`intl-adapter.js` /
`.cjs` lines 29–32, version 0.17.3). Node has a complete `Intl.Segmenter`, so
under vitest the polyfill is a no-op and
`new Intl.Segmenter('en', { granularity: 'word' })` works — then throws on
Hermes, which has no `Intl.Segmenter` at all (the table at the top of this file).
Anything written through the global therefore passes its test and crashes the
app.

So `src/core/segmenter/graphemes.ts` imports `graphemeSegments` from
`unicode-segmenter/grapheme` directly, which behaves identically on both
engines, and `test/core/segmenter/engine-boundary.test.ts` fails if any file in
that directory so much as names `Intl.Segmenter` outside a comment. The polyfill
is still what the app installs for everything above `core/`.

The consequence to carry forward: **there is no word segmenter on this engine**,
from this package or from the platform. Where a cut has to fall inside a
sentence it falls on whitespace, or on a grapheme cluster in a script written
without any.

## Offsets: two traps found in the segmenter, both silent (2026-09-19 13:38)

- **A splitter's own indices are not code units.** 1.0.31 reported
  `start_index`/`end_index` as Unicode scalar indices, its Rust strings being
  UTF-8, so `A 😀 emoji. ` ended at its 11 and at code unit 12. 0.4.2 reports no
  indices at all. Neither is trusted: each returned piece is located in the text
  from a forward-only cursor whose skipped gap must be whitespace, and a splitter
  that fails that test gets the whole block back as one utterance rather than a
  guessed offset.
- **A sentence boundary can split a grapheme cluster.** Both releases cut
  `Hello.` + U+0301 + ` World.` into `Hello.` and U+0301 + ` World.`, which hands
  a provider a bare combining mark and starts the highlight half a character
  early. Every cut is moved forward to a cluster boundary. This is not
  hypothetical: the plugin's Romanian fixture carries an NFD variant on purpose,
  and ADR 0008 records that EPUB text arrives in either normalisation.


## The segmenter, on a real book (2026-09-19 13:39)

The first time this code has seen prose nobody constructed for it: four
paragraphs from chapter 1004 of 仙逆 (耳根), a Chinese web novel from the owner's
own Downloads, run through `segmentBlocks(blocks, 'zh', …)` with the pinned
0.4.2.

Four Blocks became five Utterances, every one Speakable, and the **span
invariant held exactly — zero violations**. The cuts fell on `！` and `。`, and
the opening `“` of a quoted passage stayed with the sentence it opens.

This does **not** close item 7. Four paragraphs of one book is a spot check, and
what item 7 asks for is quality across real books. What it does settle is that
the offset machinery survives contact with text that was not written to exercise
it, which is the part that would have failed silently.

Worth recording about Chinese specifically, because it reads worse on paper than
it is. `zh` is **not** among 0.4.2's thirty languages, so it falls back to
English rules. Measured rather than assumed, the fallback costs almost nothing
here: unquoted prose, consecutive dialogue and `？！` all split correctly, and
`ja` — which *is* in the list — returns byte-identical results on the same
inputs. The one difference is that the English quote-pair rule protects
`“…”`, so `他说：“我不知道。”然后离开了。` stays one Utterance. That is arguably
what a reader wants anyway: the quotation and its attribution are one breath.
The damage is a coarser Utterance, never wrong text, and word timings still
highlight inside it word by word.


## Two things only a device could find, and the second is not written down anywhere (2026-09-19 16:08)

The word highlight did not paint. Everything upstream of it was correct — the
speak message carried the right Block ids and offsets, the Block text at those
offsets equalled the Utterance's, `domRange()` built a Range, `CSS.highlights`
accepted the `Highlight`, `::highlight()` parsed into `cssRules`, and the Range
stringified to exactly the word. The page stayed blank.

**Holding DOM nodes across renders.** The first cause, and the ordinary one: the
Block records held `parts`, `element` and `contents` from the document they were
walked from, and epub.js replaces that document — which is what a paginated
reader does. The range builder then found no browsing context and returned null.
Worth knowing: `isConnected` cannot detect this. A detached document still owns
its nodes and they still report themselves connected *to it*.
`node.ownerDocument.defaultView` is the question that answers. The record now
holds `text`, `cfi` and `section` — the things that survive — and resolves to
live nodes at paint time.

**`user-select: none` silently stops `::highlight()` from painting.** Fixing the
records changed nothing, and the bisection on the simulator is the finding:

| Where | paints? |
|---|---|
| WebView top frame | yes |
| a sibling sandboxed `srcdoc` iframe | yes |
| epub.js's iframe, from either realm | **no** |
| epub.js's iframe with the multicol layout removed | **no** |
| epub.js's iframe with `user-select: text` | **yes** |

WebKit paints a custom highlight through the same machinery it paints a
selection with, so text declared unselectable gets no highlight geometry at all.
`@epubjs-react-native/core`'s `template.js:151-155` sets `user-select: none` on
the body whenever `enableSelection` is false — its default, and ours. Nothing
about the failure resembles its cause, and the interaction is documented
nowhere: not in the CSS Custom Highlight API spec, not in WebKit's notes, not in
the library's.

The renderer's own stylesheet now forces `user-select: text` and keeps
`-webkit-touch-callout: none`, which is the property that actually suppresses the
long-press menu — the part `enableSelection: false` was really buying. Order is
load-bearing: flipping `user-select` *after* a `Highlight` is registered does not
repaint it, so the style goes in before any `put()`.

This is the second time today that a library's default was the one value its own
code refuses to work with — see the `start(when = 0, offset = -1)` wrapper in
react-native-audio-api, whose default is rejected by its own guard on the next
line. Neither is findable by reading the code that calls them.


## A cover page with no text is a dead end, and epub.js rewrites more than I said (2026-09-19 18:31)

A 33 MB book, 2,077 spine items, opened to a blank page and "Waiting for the
document to render its first section" with no way forward. The section had
rendered. `OEBPS/Text/cover.xhtml` is an empty hidden `h2` and an SVG image —
**zero readable text** — so the walk reported no Blocks and the app sat on a
state whose only message was false. Most EPUBs begin this way; the fixture book
used until now happens to open on prose, which is why nothing caught it.

A second defect surfaced while fixing it: the highlighter adopted sections only
on epub.js's `rendered`, which does not reach a listener registered later for a
view replaced by `display()`. Walking forward stalled after one hop. It now also
sweeps on `relocated`.

**And a correction to my own diagnosis, which was wrong.** I had concluded from
grepping for `querySelectorAll` that epub.js does not rewrite `<image
xlink:href>` inside SVG, and that this was why the cover was blank. It does
rewrite it — through a `spine.hooks.serialize` hook that substitutes over the
serialized section text, so every spelling is covered; the selector walks I found
are link handling and image *load* listeners. Measured in the injected realm on
the real book: the attribute already held a `blob:` URL, fetching it from inside
the iframe returned 1,293,650 bytes of `image/jpeg`, the element was visible and
hit-testable at 364×485, and substituting a 1.7 MB `data:` URL changed nothing.
Spine item 0 alone paints nothing while every later section paints, images and
all. Unexplained. The lesson worth keeping is the method: **a grep for one
mechanism cannot rule out a second one**, and the answer came from the device,
not the source tree.


## Real speech, real Word Timings, and a timing that runs past the end of the audio (2026-09-19 19:05)

The owner's own Kokoro-FastAPI, reached over the network for the first time,
which is the first real audio this project has had. `POST /dev/captioned_speech`
with `response_format: pcm` answers JSON: `audio` as base64, `audio_format:
audio/pcm`, and `timestamps` as `{word, start_time, end_time}`.

**The rate is 24 kHz**, settled by asking the plain route for `wav` and reading
the RIFF header rather than inferring it — an inference I made first and got
wrong. The captioned route names no rate at all, so a client has to assume one,
and `providers/audio.ts` assuming 24 kHz is right for this server.

The finding is what the timings do at the end:

```
PCM 104,560 bytes at 24 kHz → 2.178 s of audio

  Alpha      0.010 → 0.297
  bravo      0.297 → 0.710
  charlie    0.710 → 1.072
  delta      1.072 → 1.410
  echo       1.410 → 2.110
  .          2.110 → 2.335   ← 0.157 s past the end of the audio
```

Every real word lands inside the audio. The entry that overruns is the **full
stop**, reported as though it were a word with a duration. There is no sound for
it; the number is the server's, extrapolated, and ADR 0005 forbids exactly this
kind of value — a timing that was not measured. Driven straight into the
highlight it would park a mark on nothing for a sixth of a second at the end of
every sentence, which is small, constant, and precisely the sort of thing that
reads as "the highlight is slightly off" without ever being traced.

It is already answerable with a rule the project has: a full stop contains
neither a letter nor a digit, so it is not **Speakable**, and a timing for
something that is not Speakable can be dropped in the provider rather than
carried to the renderer.

Also measured, and a gap rather than a defect: the server sits behind Cloudflare
Access and answers only with a service token — `CF-Access-Client-Id` and
`CF-Access-Client-Secret` — sent as request headers. `local/kokoro.ts` accepts
gateway headers; the settings sheet has no field for them, so the app cannot
reach this server even though the provider layer can. 403 without them, 200
with.


## `scrolled-continuous` on the device: what scrolls, and what is alive (2026-09-19 20:05)

Measured on the iPhone 17 simulator, iOS 27, with `reading-aloud.epub` and with
the owner's 仙逆 (耳根), 34,453,009 bytes, 2,077 spine items — `book.spine.length`
read from inside the WebView, so the count is the book's and not the file
listing's.

**The element that scrolls is `rendition.manager.container`.** Read off the live
manager: `flow: "scrolled-continuous"`, `manager.name: "continuous"`,
`manager.settings.axis: "vertical"`, `manager.overflow: "scroll"`, container
`clientHeight` 570 and `scrollHeight` 9,470 on the big book. It is the
`epub-container` div the manager's own `Stage` builds inside `#viewer`, which is
why the centring reads it off the manager rather than looking an id up — the
library's template gives `#viewer` `overflow: hidden !important` and the scrolling
happens one level in.

**Several sections are alive, and the number is three.** `manager.views.all()`
returned 3 throughout a 250-Utterance reading of the big book, with 2 of them
carrying `contents`; on the two-section fixture it is 2. Each section's iframe is
as tall as its own text — 3,206 px and 3,174 px for two chapters — which is what
makes a `Range`'s client rect plus its `frameElement`'s rect equal a position on
the screen.

**The centring lands within a pixel.** Error between the middle of the painted
Utterance and the middle of the container, measured from the registered
`Highlight`'s own ranges rather than from the code that placed them: **0.05 px,
0.25 px, 0.78 px, 0.97 px** on four Utterances. One measurement came back

## An EPUB's central directory is a checksum of the whole book (2026-09-19 23:19)

Looking for a way out of the 14.4 s hash (the 22:23 measurement), because the
file is 34 MB and Hermes does SHA-256 at about 2.4 MB/s.

`仙逆 (耳根).epub`, 34,453,009 bytes:

- 2,106 members; central directory **154,535 bytes**, starting 154,557 bytes from
  the end — **0.45%** of the file.
- The first 38 bytes are `PK\x03\x04…mimetype`, which EPUB's packaging rule makes
  byte-identical in every conforming file. Hashing the head is worth nothing.
- Each central directory record carries the member's **CRC-32 of its uncompressed
  bytes**, its uncompressed size and its name.

Digesting `(name, crc32, uncompressed size)` per member reads **220,092 bytes —
0.64% of the file** — and takes **3.8 ms** in Node.

**Repacked the whole archive at two deflate levels and compared.** Python
`zipfile`, same members, same contents:

| | bytes | full-file SHA-256 | manifest digest |
| --- | --- | --- | --- |
| as the owner has it | 34,453,009 | `e933d9c4…` | `5559b6de…` |
| level 1 | 35,309,536 | `d1b0c681…` | `5559b6de…` |
| level 9 | 34,429,453 | `e535efea…` | `5559b6de…` |

So the manifest digest is invariant under re-compression and the file hash is
not. That is a property, not a coincidence: CRC-32 in a ZIP is computed over the
*uncompressed* data.

Two things that look like improvements and destroy the property, both checked
against the table above rather than reasoned about: including the **file length**
(it differs in all three rows), and hashing the **tail's raw bytes** (those carry
each member's compressed size and offset, which differ in all three rows).

**The `ncx` lies about its own depth.** `<meta name="dtb:depth" content="3"/>`,
and the file has two levels. Calibre 6.26.0 wrote it. So nothing may read
`dtb:depth`; the depth comes from walking the tree.

**The spine compresses to three literals and a run.** All 2,077 hrefs are
`Text/cover.xhtml`, `Text/copyright.xhtml`, `Text/introduction.xhtml`, then
`Text/chapter1.xhtml` … `Text/chapter2074.xhtml` in order — checked against every
one of the 2,074 `itemref`s, not inferred. So `Text/chapterN.xhtml` is spine item
`N + 2`, and a committed fixture can hold the real spine whole while the
navigation is sliced.

**The navigation's hrefs are not resolved by epub.js, and neither are the
spine's.** `Navigation.ncxItem` returns the raw `<content src>`; the spine's href
is the raw manifest href. They are relative to different files and happen to be
byte-identical here because `toc.ncx` sits beside `content.opf`. A book whose
navigation lives in another directory therefore matches **nothing** — all rows,
not one row, which is the only reason a string match is safe to ship.

**`navPoint` ids are not strings.** `ncxItem` computes
`getAttribute('id') || false`, so a `navPoint` with no `id` yields the boolean
`false`, while a navigation document's `navItem` falls back to the *href* — so two
entries pointing at one file share an id. `@epubjs-react-native/core`'s own type
says `id: string` (`lib/typescript/types.d.ts:66-72`). Nesting must be read from
`subitems`, never from `parent`, which is that same id.

### What "where am I" can be answered from, and what it cannot

A navigation entry is an href into the spine; the reading position is a Block id,
a CFI and a spine index. Only the **spine index** connects the two. The Block id
is `sectionIndex + '.' + ordinal` (`src/renderer/highlighter.ts:334`) so the spine
index is in it as a decimal prefix, and a CFI's first component encodes the spine
position — but both are second spellings of a number `ReportedBlock.sectionIndex`
already carries across the bridge, and decoding the CFI would put epub.js's CFI
dialect inside `src/core/`, which is what ADR 0008 keeps out.

So resolution is at **spine-item granularity and no finer**, and the two things it
cannot do are worth naming because on this book neither is visible:

- **Several entries in one file.** They differ only by `#fragment`, a fragment
  names an element, and where an element falls needs the rendered document. This
  book has zero fragments, so it never happens here — and a book that puts a
  part's title and its chapters in one file is ordinary.
- **A spine item no entry names.** Happens here exactly once, at spine item 1, so
  reading the copyright page reports the cover.

### Two conversions that raise `URIError`, and epub.js lets them

`decodeURI('Text/a%zz.xhtml')` and `encodeURI('Text/\uD800.xhtml')` both throw.
epub.js calls both unguarded in `Spine.append`, inside `unpack`, so a single
malformed spine href loses the whole book rather than one section. Guarded here:
a spelling that cannot be computed is simply not registered.
