## Library Search scroll-collapse diagnostic (2026-10-28, ios-tester, parent follow-up)

Unchanged beta1 (`6f73fad`, build untouched), same device/Metro/DerivedData.
Question: is the standing search field an initial-layout state (H1), a list
never associated with the header's collapse (H2), or a collapse that something
re-expands (H3)?

- **H2 confirmed.** With the FlatList genuinely scrolled to offset 400 (twelve
  temporary `Scroll Diag NN of 12` fixtures; rows 12–10 out of view), the
  native field stayed standing, interactive and in an unchanged 114 pt header —
  `hidesSearchBarWhenScrolling` never collapses this bar. Not H1 (it is not
  merely the initial state) and not H3 (it never collapses to re-expand). The
  list itself scrolls normally, so the field is the only thing frozen in the
  header. Consistent with `RNSScreenStackHeaderConfig.mm:607` setting the prop
  on a navigation item whose search bar UIKit never associates with the React
  scroll view.
- **Touch path:** on this device, XCUITest coordinate press-drags and
  `swipeUp(velocity: .fast)` do not scroll the list at all (pixel-identical
  before/after), while XCUITest taps and typing land. The collapse check
  therefore drove the FlatList's own `scrollToOffset` through
  `cdp.cjs --eval` (fiber walk, the `reading.cjs` pattern; evaluator scripts
  in `/tmp/openreader-search-332-01/diag-scroll-drive.js` and
  `diag-scroll-restore.js`, both returning `{found: true, rows: 13}`).
- **One-row/empty content:** no scroll offset is reachable, so no collapse is
  observable; all four frame records (cold, after swipe, settled, after
  pull-down) identical, field `{{16, 117}, {370, 44}}`, row `{{0, 188},
  {402, 84}}`, `keyboards.count` 0. Expanded header geometry from the AX tree:
  `NavigationBar {{0, 62}, {402, 114}}` containing the field; content starts
  y≈188.
- Environment churn during the run: the sibling #330 session's platform work
  shut this device down twice (my boots; never touched their lane or data);

## LLDB finds why the beta2 binding is a no-op (2026-10-28 14:33)

Direct native inspection on the installed beta2 (PID 76591, session device)
reported `cached=0x0 lookup=0x0 observed=0x0`, while the search controller was
present, `hides=1 active=0`, and the navigation bar was still `(0,62,402,114)`.
The existing descendant lookup returned no scroll view; the patch never
registered one. This supersedes the stronger interpretation that a valid
`setContentScrollView:forEdge:` binding did not work.

A breadth-first read of the view hierarchy found:

- `RNSScreenView` → `RNSScreenContentWrapper` → `RNSSafeAreaViewComponentView`.
- Its first child was an empty `RCTViewComponentView` background. The next
  sibling was another `RCTViewComponentView` containing the actual
  `RCTScrollViewComponentView` / `RCTEnhancedScrollView`.
- The actual list had frame `(0,0,402,874)`, content `(402,1116)`, offset
  `(0,-176)`, adjusted inset `(176,0,34,0)`, and explicit inset zero.

The first-child lookup stops at the empty background, and the existing iOS 26
fallback looks only at immediate safe-area children. Beta3 adds a search-only
breadth-first fallback and an initial collapsed offset measured from the
native search bar's own laid-out height. Native acceptance remains pending.

The MCP/CLI debugger's default DAP backend attached successfully but refused
expression evaluation; it was explicitly detached. The guarded direct LLDB
fallback produced the measurements and explicitly detached. Two expression
compile failures preceded the successful read: LLDB needed an explicit `Class`
cast for `[screen class]` when `screen` was typed `id`; those runs also left the
app running. Artifacts: `native-binding/`, `native-binding-lldb*.log`,
`native-scrollviews.log` and their guard records under the same attempt dir.

A planned live binding/offset experiment did not execute: its attach found no
such PID, and the subsequent device listing showed no booted simulators. The
session device was shut down during the interval; no cause is established by
that observation. Parent Metro 8332 (PID 23282) remained alive. No runtime
