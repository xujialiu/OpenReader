## npm will not search downward for a peer it has already locked (2026-09-23 02:44)

npm 10.9.8, node v22.23.2, `main` at 0c2674b, no `node_modules`, no `.npmrc` in the repository or in `$HOME`, `npm config get legacy-peer-deps` = `false`.

`npm ci --dry-run --ignore-scripts` exits 1 in 0.64 s with `Conflicting peer dependency: react@19.3.0`. That is the whole signal for #42 and it needs no network beyond the registry metadata npm already has.

Copying `package.json` and `package-lock.json` into an empty directory and running **`npm install --package-lock-only --ignore-scripts` with no flags fails the same way**. npm keeps the `react-dom@19.3.0` the lockfile already names and reports the conflict; it does not try 19.2.x to find one whose peer `react@19.2.3` satisfies. So a lockfile in this state cannot be rewritten out of it — the version has to be named.

Naming it with `"overrides": { "react-dom": "$react" }` and re-running the same command changes exactly two nodes:

| | before | after |
| --- | --- | --- |
| `node_modules/react-dom` | 19.3.0 | 19.2.3 |
| `node_modules/react-dom/node_modules/scheduler` | 0.28.0 | gone — 19.2.3 wants `^0.27.0` and shares the root 0.27.0 |

17 changed lines in `package-lock.json`, nothing else in the tree moves, and `npm ci --dry-run` then exits 0.

A caret would not have done: `react-dom@19.2.8` is published and peers with `react@^19.2.8`, which `react@19.2.3` does not satisfy, so `^19.2.3` resolves back into a conflict. `$react` resolves to the pinned spec exactly.
