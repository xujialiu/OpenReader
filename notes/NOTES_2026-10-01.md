## epub.js's queue never settles after a task that throws (2026-10-01 02:25)

This is from `@epubjs-react-native/core` 1.4.8's `lib/commonjs/epubjs.js`, around line 1942. `Queue.run()` waits for `this.tick`, which is `requestAnimationFrame`. It then calls `dequeue()` inside the frame callback, and `dequeue()` calls the task with `e.apply(this.context, t.args)` and no `try`.

A task that throws synchronously therefore throws out of the frame callback. Its entry's deferred is never settled, and `run()` is not called again. The queue keeps `running: true` and its `_q` for good, exactly like a task whose promise never settles.

`test/renderer/renderer-log.test.ts` ports the queue method for method. I ran the port with `manager.append` throwing, under the program's own `renderAhead`. The `Error` came out of the frame callback into the test, and `renderAhead`'s rejection handler was never called. The test's failing view now rejects from `display()` instead.

Two related facts from the same file:

- `IframeView.destroy()` (around line 6027) does nothing unless the view is `displayed`, so a view removed from `Views` mid-display keeps a `display()` that never settles.
- `Views.destroy(view)` is what removes the view's element.

## iOS sheet detents, from Apple's documentation and the iOS 27 SDK header (2026-10-01 11:19)

Research for the drawers' heights (`src/app/sheet.tsx`), read from Apple's documentation JSON and from `UISheetPresentationController.h` in Xcode 27.0's `iPhoneOS.sdk` (`/Applications/Xcode-27.0.0.app/…/UIKit.framework/Headers/UISheetPresentationController.h`). Nothing here was run on a phone.

**Medium and large.** The header says, of `mediumDetent`, "A system detent for a sheet that is approximately half the height of the screen, and is inactive in compact height", and of `largeDetent`, "A system detent for a sheet at full height" (header lines 62–66). Apple's pages say the same words: `medium()` "Creates a system detent for a sheet that's approximately half the height of the screen, and is inactive in compact height" (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/detent/medium()), `large()` "Creates a system detent for a sheet at full height" (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/detent/large()). Neither the header nor the pages give a formula for medium. The two places that say more both measure it against the expanded sheet rather than the screen: WWDC21 session 10063 says detents "are defined as a fraction of the fully expanded sheet frame" and medium "is about half of a sheet's full height" (https://developer.apple.com/videos/play/wwdc2021/10063/), and the HIG says "medium is about half of the fully expanded height" (https://developer.apple.com/design/human-interface-guidelines/sheets). The exact number of points medium comes to on a given phone is not stated anywhere I read; it would have to be measured. The default `detents` is "an array of only [UISheetPresentationControllerDetent largeDetent]", and "Detents must be specified in order from smallest to largest height" (header lines 146–150; https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/detents).

**Custom detents (iOS 16).** `customDetentWithIdentifier:resolver:` / `.custom(identifier:resolver:)`: "The value returned from the resolutionContextBlock is a height within the safe area of the sheet. For example, returning 200 will result in a detent where the height of the sheet is 200 + safeAreaInsets.bottom when edge-attached, and just 200 when floating. Return nil if the detent should be inactive" (header lines 68–75; https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/detent/custom(identifier:resolver:)). The resolver's context has `maximumDetentValue`, "The maximum value a detent can have" (header line 50–51; https://developer.apple.com/documentation/uikit/uisheetpresentationcontrollerdetentresolutioncontext/maximumdetentvalue), and `resolvedValueInContext:` "may be used to get the values of the system medium and large detents" inside a resolver (header lines 82–86). So a custom detent can be written as a fraction of medium or large, but the header does not print medium's value. A detent that depends on outside state needs `invalidateDetents` (iOS 16).

**SwiftUI.** `presentationDetents(_:)` (iOS 16.0): "If you provide more that one detent, people can drag the sheet to resize it", and "By default, sheets support the large detent" (https://developer.apple.com/documentation/swiftui/view/presentationdetents(_:)); `presentationDetents(_:selection:)` adds a binding to the selected one. `PresentationDetent.medium` is "The system detent for a sheet that's approximately half the height of the screen, and is inactive in compact height"; `.large` "The system detent for a sheet at full height"; `.fraction(_:)` "A custom detent with the specified fractional height"; `.height(_:)` "A custom detent with the specified height" (https://developer.apple.com/documentation/swiftui/presentationdetent/medium, …/large, …/fraction(_:), …/height(_:)). A `CustomPresentationDetent` gets a context whose `maxDetentValue` is "The height that the presentation appears in"; Apple's own example is `max(44, context.maxDetentValue * 0.1)` (https://developer.apple.com/documentation/swiftui/presentationdetent/context/maxdetentvalue, https://developer.apple.com/documentation/swiftui/custompresentationdetent). The pages do not say what `.fraction` is a fraction of; the example suggests `maxDetentValue`, which is an inference.

**Grabber.** UIKit `prefersGrabberVisible`, default `NO` (header lines 138–140): "A grabber is a visual affordance that indicates that a sheet is resizable. Showing a grabber may be useful when it isn't apparent that a sheet can resize or when the sheet can't dismiss interactively", and the system hides it "when the sheet is full screen in a compact-height size class or when another sheet presents on top of it" (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/prefersgrabbervisible). SwiftUI `presentationDragIndicator(_:)` (iOS 16.0) takes a `Visibility`; "You can show a drag indicator when it isn't apparent that a sheet can resize or when the sheet can't dismiss interactively" (https://developer.apple.com/documentation/swiftui/view/presentationdragindicator(_:)).

**Content taller than the detent.** UIKit `prefersScrollingExpandsWhenScrolledToEdge`, default `YES`: "If there is a larger detent to expand to than the selected detent, and a descendent scroll view is scrolled to top, this controls whether scrolling down will expand to a larger detent. Useful to set to NO for non-modal sheets, where scrolling in the sheet should not expand the sheet and obscure the content above" (header lines 166–169). The page puts it the other way round: with `true`, "scrolling up in the sheet increases its detent instead of scrolling the sheet's content. After the sheet reaches its largest detent, scrolling begins" (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/prefersscrollingexpandswhenscrolledtoedge). SwiftUI's `presentationContentInteraction(_:)` (iOS 16.4): "By default, when a person swipes up on a scroll view in a resizable presentation, the presentation grows to the next detent. A scroll view embedded in the presentation only scrolls after the presentation reaches its largest size"; `.scrolls` "prioritizes scrolling the content of a presentation when swiping, rather than resizing the presentation", `.resizes` the reverse, and "People can always resize your presentation using the drag indicator" (https://developer.apple.com/documentation/swiftui/view/presentationcontentinteraction(_:), …/presentationcontentinteraction/scrolls, …/resizes). So the sheet's height is the detent's, never the content's: what does not fit is reached by a scroll view inside it, after (by default) the sheet has first grown to its largest detent. A sheet with a single detent has no larger one to grow to, so its scroll view scrolls at once — an inference from the header's "If there is a larger detent to expand to". WWDC21 10063 shows both: the share sheet "progressively discloses more advanced actions" by expanding, and a photo picker sets the property to false "so the postcard is always visible unless I explicitly resize the sheet by dragging from the bar".

**The page behind at medium.** UIKit `largestUndimmedDetentIdentifier`, default nil: "When nil or the identifier is not found in detents, all detents are dimmed" (header lines 162–164). The page: nil "means the system adds a noninteractive dimming view underneath the sheet at all detents… set this property to medium to add the dimming view at the large detent. Without a dimming view, the undimmed area around the sheet responds to user interaction, allowing for a nonmodal experience" (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller/largestundimmeddetentidentifier). Apple's own sample on the class page sets `[.medium(), .large()]`, `largestUndimmedDetentIdentifier = .medium` and `prefersScrollingExpandsWhenScrolledToEdge = false` together (https://developer.apple.com/documentation/uikit/uisheetpresentationcontroller). In WWDC21 10063 the property is spoken as "smallestUndimmedDetentIdentifier"; the iOS 27 header names it `largestUndimmedDetentIdentifier`. SwiftUI: "SwiftUI automatically disables the view behind a sheet that you present"; `presentationBackgroundInteraction(.enabled(upThrough:))` (iOS 16.4) lets people interact behind it up to that detent, and "At detents larger than the one you specify, SwiftUI disables interaction" (https://developer.apple.com/documentation/swiftui/view/presentationbackgroundinteraction(_:), https://developer.apple.com/documentation/swiftui/presentationbackgroundinteraction/enabled(upthrough:)). By default, then, the page behind a medium sheet is dimmed and does not take touches; it is undimmed and live only when the app asks.

## What the HIG's Sheets page says about detents, the grabber and scrolling (2026-10-01 11:19)

Read from the page's JSON (https://developer.apple.com/tutorials/data/design/human-interface-guidelines/sheets.json, rendered at https://developer.apple.com/design/human-interface-guidelines/sheets). Its newest change-log entry is "March 24, 2026 — Updated guidance for button placement." Under "iOS, iPadOS", verbatim:

- "A resizable sheet expands when people scroll its contents or drag the grabber, which is a small horizontal indicator that can appear at the top edge of a sheet. Sheets resize according to their detents, which are particular heights at which a sheet naturally rests. Designed for iPhone, detents specify particular heights at which a sheet naturally rests. The system defines two detents: large is the height of a fully expanded sheet and medium is about half of the fully expanded height. Sheets can have one or more custom detent values."
- "Sheets automatically support the large detent. Adding the medium detent allows the sheet to rest at both heights, whereas specifying only medium prevents the sheet from expanding to full height."
- "In an iPhone app, consider supporting the medium detent to allow progressive disclosure of the sheet's content. For example, a share sheet displays the most relevant items within the medium detent, where they're visible without resizing. To view more items, people can scroll or expand the sheet. In contrast, you might not want to support the medium detent if a sheet's content is more useful when it displays at full height. For example, the compose sheets in Messages and Mail display only at full height to give people enough room to create content."
- "Include a grabber in a resizable sheet. A grabber shows people that they can drag the sheet to resize it; they can also tap it to cycle through the detents. In addition to providing a visual indicator of resizability, a grabber also works with VoiceOver so people can resize the sheet without seeing the screen."
- "Support swiping to dismiss a sheet. People expect to swipe vertically to dismiss a sheet instead of tapping a dismiss button."

On modality: "In iOS and iPadOS, a sheet can be either modal or nonmodal. When a nonmodal sheet is onscreen, people use its functionality to affect the parent view without dismissing the sheet. For example, Notes on iPhone and iPad uses a nonmodal sheet to let people format various text selections as they edit a note." And under best practices: "Use a nonmodal view when you want to present supplementary items that affect the main task in the parent view… in iOS and iPadOS, you can use a nonmodal sheet for this workflow." Also "Display only one sheet at a time from the main interface", and "The Back button lets people navigate to a previous step in a multi-step flow or to a parent view in a hierarchy. It isn't intended to dismiss a sheet." For a single-view sheet, "the Cancel button belongs on the leading edge of the top toolbar" and Done on the trailing edge. The page's two detent illustrations are described as a sheet that "occupies almost all of the screen" (large) and one that "occupies half of the screen" (medium), each with "A rounded close button… in the upper-left corner of the sheet" (image alt texts `sheets-large-detent.png`, `sheets-medium-detent.png`). The page says nothing more specific about scrolling than the sentences quoted.

## @expo/ui 57.0.19's BottomSheet, and what React Native's Modal and react-native-screens offer (2026-10-01 11:20)

Installed here: `@expo/ui` 57.0.19 (`node_modules/@expo/ui/package.json`; `package.json:19` asks for `~57.0.19`), `expo` 57.0.24, `react-native` 0.86.3, `react-native-screens` 4.26.2, `@react-navigation/native-stack` 7.19.2. The app already imports `@expo/ui` in `src/app/controls.tsx`, `player.tsx` and `reading-button.tsx`. `ChoiceMenu` hosts React Native rows in a SwiftUI `Menu` through `RNHostView` (`src/app/controls.tsx:518–533`).

**The SwiftUI `BottomSheet`** (https://docs.expo.dev/versions/v57.0.0/sdk/ui/swift-ui/bottomsheet/, page dated August 18, 2026) "matches the official SwiftUI sheet API". Its props are `isPresented`, `onIsPresentedChange`, `onDismiss`, `anchor` and `fitToContents` (`node_modules/@expo/ui/build/swift-ui/BottomSheet/index.d.ts:3–32`). In Swift it is a plain `.sheet(isPresented:onDismiss:)` on the anchor (`node_modules/@expo/ui/ios/BottomSheetView.swift:105–111`). `fitToContents` measures the children and sets `.presentationDetents([.height(childrenSize.height)])`, or `[.medium]` before the first measurement (`BottomSheetView.swift:81–87`). The children "mounted while presented and unmounted after dismiss" (`index.d.ts:5–6`), and the JS side unmounts them only in `onDismiss` (`node_modules/@expo/ui/src/swift-ui/BottomSheet/index.tsx`).

**Presentation modifiers**, applied to a `Group` wrapping the sheet's content (`node_modules/@expo/ui/build/swift-ui/modifiers/presentationModifiers.d.ts`; `ios/Modifiers/PresentationModifiers.swift`; https://docs.expo.dev/versions/v57.0.0/sdk/ui/swift-ui/modifiers/):

- `presentationDetents(detents, { selection, onSelectionChange })` takes `'medium' | 'large' | { fraction } | { height }`. These map one to one onto SwiftUI's `.medium`, `.large`, `.fraction()` and `.height()` (`PresentationModifiers.swift:19–39`). An empty list becomes `[.large]` (`:55–65`). The sheet opens at the first detent in the array, not at a random member of the Set (`:127–130`). The .d.ts glosses `fraction` as "Fraction of screen height (0-1, for example, 0.4 equals to 40% of screen)" (`presentationModifiers.d.ts:7`); Apple's page does not say what it is a fraction of (entry above).
- `presentationDragIndicator('automatic' | 'visible' | 'hidden')` (`:151–161`).
- `presentationBackgroundInteraction('automatic' | 'enabled' | 'disabled' | { type: 'enabledUpThrough', detent })` (`:165–196`), iOS 16.4+. The versioned page's own example is `presentationDetents(['medium', 'large'])` with `presentationBackgroundInteraction({ type: 'enabledUpThrough', detent: 'medium' })`, and "Interact with content behind when at medium height."
- `presentationBackground(style)`, `interactiveDismissDisabled`, `presentationSizing` (iOS 18).
- **There is no `presentationContentInteraction`** (`.scrolls` / `.resizes`): `grep -rn contentInteraction` over `node_modules/@expo/ui/{ios,build,src}` finds nothing, and the v57 modifiers page lists none. With `['medium', 'large']`, swiping up on content therefore takes SwiftUI's default: the sheet grows to large first, then scrolls (entry above). The way round that within these modifiers is a single detent. That is an inference.

**React Native content inside it.** `RNHostView` "enables React Native views inside SwiftUI"; with `matchContents` the host takes the RN child's size, and without it "the shadow node size is set to match the parent SwiftUI view's size, allowing the React Native content to fill the available space (useful for `flex: 1` layouts)". It also notes: "Pass a single React Native element as the child" (https://docs.expo.dev/versions/v57.0.0/sdk/ui/swift-ui/rnhostview/, dated August 31, 2026). Inside a sheet, `RNHostView` attaches its own touch handler, "Presented in its own view controller, so nothing above dispatches and the content would get no touches at all" (`node_modules/@expo/ui/ios/RNHostView.swift:23–35`, and `src/swift-ui/RNHostView.tsx` sets `layoutRoot` from `useIsPresentedInOwnWindow()`). The BottomSheet page's "Scrollable React Native content" section: "Nest a scrollable React Native list such as `FlatList`, `ScrollView`… inside the sheet with `RNHostView`. Size the sheet with `presentationDetents` and the list scrolls within that height". Its example is a 50-row `FlatList` under `presentationDetents(['medium', 'large'])` and `presentationDragIndicator('visible')`. The page says nothing about the keyboard, or about how a nested RN `ScrollView` hands off to the sheet's own drag. Neither was tried here. One related statement, from an Expo maintainer on a different component (`Host` in lists, SDK 57): "`UIHostingController` adds default safe area insets to SwiftUI content and it does not work well with RN layout… making `ignoreSafeArea=\"all\"` as default… would be a breaking change for keyboard support with TextFields" (https://github.com/expo/expo/issues/40604, read from the search provider's extract of the thread, not the page itself).

**The universal `BottomSheet`** (`import { BottomSheet } from '@expo/ui'`; https://docs.expo.dev/versions/v57.0.0/sdk/ui/universal/bottomsheet/) has `snapPoints` of `'half' | 'full' | { fraction } | { height }`, and "When omitted, the sheet auto-sizes to its content". It also says "When sheet content can be taller than the smallest snap point, wrap it in a `ScrollView` so the overflow scrolls correctly". On iOS it maps `'half'` → `'medium'` and `'full'` → `'large'` and wraps the SwiftUI sheet. The drag indicator is visible by default, the padding is 16 pt top, left and right and 0 bottom, and with no snap points it sets `fitToContents` (`node_modules/@expo/ui/src/universal/BottomSheet/index.ios.tsx`).

**React Native's own `Modal`** (0.86.3) has `presentationStyle?: 'fullScreen' | 'pageSheet' | 'formSheet' | 'overFullScreen'`, plus `allowSwipeDismissal` and `backdropColor` (`node_modules/react-native/Libraries/Modal/Modal.js:102–155`). It has **no detent prop**. On Fabric, `pageSheet` becomes `UIModalPresentationPageSheet` and `formSheet` becomes `UIModalPresentationFormSheet`, and `transparent` overrides both to `UIModalPresentationOverFullScreen` (`React/Fabric/Mounting/ComponentViews/Modal/RCTModalHostViewComponentView.mm:73–99`). Nothing in that folder touches `sheetPresentationController` or detents (`grep` finds none). A page or form sheet on iPhone therefore keeps UIKit's default `[largeDetent]`, a full-height card (an inference from the header's default above). The app's `Sheet` uses `<Modal transparent animationType="slide">` (`src/app/sheet.tsx:53`), so it is an over-full-screen view that draws its own card.

**react-native-screens' form sheet** (already a dependency through native-stack) does expose detents: `sheetAllowedDetents?: number[] | 'fitToContents'` (fractions, ascending; "Defaults to `[1.0]`"), `sheetGrabberVisible` (default `false`), `sheetLargestUndimmedDetentIndex` (default `none`), `sheetExpandsWhenScrolledToEdge` (default `true`) and `sheetInitialDetentIndex` (`node_modules/react-native-screens/lib/typescript/types.d.ts:318–411`). Its legacy `'medium'` "corresponds to `[0.5]` detent value, around half of the screen height". Its own remark: "On iOS, the native implementation might resize the the sheet w/o explicitly changing the detent level, e.g. in case of keyboard appearance" (`types.d.ts`, under `sheetLargestUndimmedDetentIndex`). native-stack 7.19.2 passes `sheetAllowedDetents?: number[] | 'fitToContents'` through for `presentation: 'formSheet'` (`node_modules/@react-navigation/native-stack/lib/typescript/src/types.d.ts:631`). Using it would make each drawer a screen in the navigator rather than a component on the reader's screen; I did not look into what that changes.
