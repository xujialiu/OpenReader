## `Transaction` is ambiguous in our StoreKit module: ExpoModulesCore brings SwiftUI (2026-10-09 15:10)

The first compile of `modules/open-reader-store` (#148) was on `xujialiu/in_app_purchase--iap`. A clean `CI=1 npx expo prebuild --platform ios` exited 0 with CocoaPods installed. Then `xcodebuild -workspace ios/OpenReader.xcworkspace -scheme OpenReader -configuration Debug -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' -derivedDataPath <scratch> ENABLE_USER_SCRIPT_SANDBOXING=NO -quiet build` exited 65, with one Swift error, in `SwiftCompile normal x86_64 (in target 'OpenReaderStore' from project 'Pods')`:

```text
OpenReaderStoreModule.swift:119:47: error: 'Transaction' is ambiguous for type lookup in this context
StoreKit.Transaction:2:15: note: found this candidate
SwiftUI.Transaction:2:23: note: found this candidate
```

Only the parameter type `_ transaction: Transaction` failed. The calls `Transaction.updates`, `.currentEntitlements` and `.latest(for:)` were renamed too, to keep one spelling. With every use spelled `StoreKit.Transaction`, the incremental build exited 0. Its log still holds 14 lines `error: the following command failed with exit code 0 but produced no further output`, which the release guide already lists as harmless. The `async throws` `AsyncFunction` closures compiled under the pod's `swift_version = '5.9'` without a concurrency error.

The generated scheme then held `<StoreKitConfigurationFileReference identifier = "../../storekit/OpenReader.storekit">` as the last child of `<LaunchAction>`, written by `plugins/with-storekit-configuration.ts`. Whether Xcode resolves that path was not tried.

## The lock in the plain release bundle: `var PURCHASE_LOCK = true;` (2026-10-09 15:22)

`npx expo export:embed --platform ios --dev false --minify false --entry-file index.ts`, run once under `env -u EXPO_PUBLIC_OPENREADER_UNLOCKED -u EXPO_PUBLIC_OPENREADER_DEBUG_MODE` and once with `EXPO_PUBLIC_OPENREADER_UNLOCKED=1`, both exited 0. In the bundles they wrote:

| Bundle | `grep -o 'var PURCHASE_LOCK = [a-z]*;'` | `grep -o 'var DEBUG_MODE = [a-z]*;'` |
| --- | --- | --- |
| Variable unset | `var PURCHASE_LOCK = true;` | `var DEBUG_MODE = false;` |
| `EXPO_PUBLIC_OPENREADER_UNLOCKED=1` | `var PURCHASE_LOCK = false;` | `var DEBUG_MODE = false;` |

The second run came straight after the first with no cache clean, so Metro's cache key kept the two apart, as ADR 0054 measured for Debug Mode.

The same two runs **minified** (the `export:embed` default) keep no name to grep. They read `"PURCHASE_LOCK",{enumerable:!0,get:function(){return t}});var t=!0` with the variable unset, and `var t=!1` with it set. The release guide's grep is against the archive's plain `main.jsbundle`, as its `DEBUG_MODE` check already is.

## The Trial and the Unlock on the simulator, 1.0.0 (7)-beta11 to beta13 (2026-10-09 17:56)

ios-tester ran on "iPhone 17 in_app_purchase" (`3DA2AC49-6A30-4F11-A514-6E1DEBCBF93C`, iOS 27.0), with the pretend App Store of Debug Mode, Metro on 8082 and a fake Kokoro server. Every press was silenced and checked first. The full measurements, with raw lines, are in `test/manual-test/purchase/README.md` ("Measured on beta11 / beta12 / beta13").

- **beta11.** All eight items passed on function: the alerts' wording, the outcomes, the end of the Trial reached mid-use, a Pronunciation's resume, the downloads' gate, the Lock Screen, saved narration, and the purchase question before Consent. Real StoreKit on this simulator, launched by `simctl` with no StoreKit configuration, loaded both products (`$4.99`, `$0.00`) in 1.3 s, and `AppTransaction.shared` threw (`StoreKit environment: unavailable`). Two findings came out of it. First, the Download drawer read "Interrupted · continues when available", then "Queued" with "Pause all", over a download that could not run. Second, a refused Lock Screen Play left the button on Pause (`LockScreenProbe` 85 s later).
- **beta12.** Downloads at the end of the Trial end Paused: a 7 s Trial ended at 17:23:02.821, the pause was logged at 17:23:02.874, and no request followed. No continued task is submitted while locked. "No Purchase Found" and the Purchase row passed. Restore with `"use":"real"` raised the system's "Sign in to Apple Account" sheet, and cancelling it logged `UnexpectedException: Request Canceled` with nothing shown. The Lock Screen still failed: writing the same paused state moved nothing in `mediaremoted`.
- **beta13.** A playing write, then a paused one 400 ms later, made `mediaremoted` log Paused→Playing→Paused (17:51:49.109 / 17:51:49.501), and `LockScreenProbe` read Play 51 s later. The kit's `play` test failed on the refused press (`Executed 1 test, with 1 failure`) and left xcodebuild in `simctl diagnose` for about 5 minutes. `lock-device.sh … play-refused` replaces it for this case.
