## Library two-finger pan loses vertical gestures to its ScrollView (2026-10-04 05:59)

On the session iPhone 17 Pro Max / iOS 27.0 simulator, beta4's ordinary pan (two pointers, distance zero, JavaScript callbacks) reliably handled the horizontal entry in the corrected `LibraryTwoFingerProbe.testEdgeHoldAutoScrollsRange`, but the following vertical sweep did not call its start callback. Targeted temporary logs instead recorded native ScrollView offsets down to approximately -261 points. The corrected probe failed twice with selection remaining zero; raw results are `/tmp/openreader-sel128-parent/test-20261004-041013.log` and `test-20261004-041213.log`.

Explicitly placing a native recognizer on the Library ScrollView, requiring it to wait for the selection pan to fail, made the same edge test pass. The following four-method run passed, including actual single-finger scrolling, two-finger addition/removal and Cancel: `/tmp/openreader-sel128-parent/test-20261004-055643.log`, `Executed 4 tests, with 0 failures`, 49.284 seconds. A fifth single-contact reversal check was then added for the final tester pass. The chapter drawer keeps its previous attachment; only the Library installs the native dependency.

The rejected manual-activation experiment emitted `[react-native-gesture-handler] react-native-reanimated is required in order to use synchronous state management`; no dependency was added. All `[DEBUG-128-sweep]` instrumentation and manual activation were removed before final verification.

The original tester's failed runs also contained wrong-Metro launches, an expected-five count for a six-row path, and an edge hold outside the active band starting from row 7 but expecting eight selected out of ten total rows. The raw fourth run did not establish automatic exit at zero: its preceding entry gesture had already failed. Those are preserved and corrected in `test/manual-test/library-and-reader/library-two-finger.md`, not reclassified as passing runs.
