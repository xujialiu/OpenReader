# Purchase and release-copy verification

Read [release-variants.md](release-variants.md) before testing the formal,
free or Debug copy (#324). Native role, Metro role and the version label must
agree; Xcode Debug/Release configuration does not choose the product role.

| Role | Purchase behavior | Runtime purchase record |
| --- | --- | --- |
| Formal | Real StoreKit; existing Trial/Unlock and source-bound fallback | `Library/Application Support/purchase.json` |
| Free | All features; no purchase module, UI or controller | Untouched |
| Debug | The same free access, with diagnostics | Untouched |

Debug has no pretend store and no `store` harness command. Use the formal
variant for purchase testing. Its Xcode-launched Run action names
`storekit/OpenReader.storekit`; `simctl`, `expo run:ios` and bare xcodebuild
do not activate that scheme configuration. Claim real local StoreKit
transactions only when that environment was actually established.

Host coverage: `test/build/`, `test/purchase/`, `test/app/purchase-*` and
`test/offline/runtime-purchase*`. These cover identity, physical-exclusion
contracts, cache/source isolation, Trial arithmetic, speech/Download gates,
Restore/refund behavior and free → formal handoff. Mocks do not establish
App Store, TestFlight or purchasing-account-switch behavior.

## Genuine local StoreKit without the Xcode GUI (#345, 2026-11-06)

A supported SKTestSession arrangement exists for headless runs: a UI test
target ATTACHED to the formal app target (`TEST_TARGET_NAME=OpenReader`, added
by `purchase/add-storekit-ui-target.rb`) with the shared scheme's LaunchAction
naming `storekit/OpenReader.storekit`, run by `purchase/run-storekit-ui.sh`
(Release configuration). Measured on the SDK57 formal app and re-verified after
overlaying the SDK58 formal build: `StoreKitSessionUI.swift` buys the Trial and
the Unlock with `disableDialogs` and the app's own Purchase row reads
`Purchase, 30 days left` then `Purchase, Unlocked`; `test03` re-opens the same
configuration, requires both original transaction identities
(`SKTestTransaction.identifier`, compared against the ledger captured at
establish) and the still-`Unlocked` row without buying. `purchase.json` was
byte-identical across the overlay. The traps, each measured:

- **An UNATTACHED runner-process `SKTestSession` does NOT govern the app.** A
  standalone ui_test_bundle (`kit/project.rb` shape) bought transactions its
  session could see (`PROBE-TRANSACTIONS-AFTER 1 [...]`) while the app's row
  stayed empty. Do not claim purchases from an unattached session.
- **`TEST_RUNNER_`-prefixed environment did not reach the runner here.** The
  mode travels in the scheme's TestAction EnvironmentVariables
  (`purchase/set-scheme-env.rb`), and `shouldUseLaunchSchemeArgsEnv="YES"` on
  the generated TestAction silences them — it must be `NO`. Fail closed: no
  mode variable, every test skips, and the host checks the raw
  `PROBE-MODE …` markers instead of trusting exit codes.
- **Swift `throws` test methods bridge as `…AndReturnError:`**, so
  `-only-testing:Class/methodName` by the Swift name selects 0 tests and
  xcodebuild reports a "passed" suite with zero tests. Give tests explicit
  `@objc(name AndReturnError:)` selectors, and treat "Executed 0 tests" as a
  setup failure, never a pass.
- **xcodeproj-created ui_test_bundle targets have no `PRODUCT_NAME`**; the
  build then collides producing `-Runner.app/.xctest`. Set
  `PRODUCT_NAME=$(TARGET_NAME)` on creation and re-apply it when reusing a
  project generated by an earlier run.
- **The local StoreKitTest store persists across processes** (kept transaction
  identities survived new `xcodebuild test` runs), and the app's
  `purchase.json` record fallback keeps `Unlocked` even after the store is
  cleared — a clean-establish run must delete the record file first, or the
  first row check reads `Unlocked` before any purchase of that run.
- A formal (Release) build writes no Debug Log; verify formal installs through
  the visible Settings version/Purchase rows and the embedded-bundle verifier,
  never through a debug launch line.
