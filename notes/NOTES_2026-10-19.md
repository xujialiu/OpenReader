| 22:20:20.723 | 22:20:22.740 | 2.017 s | 22:20:34.234, `play: ok` (13.5 s) |

Each of the three came less than a minute after a run had failed for want of a reply (22:19:15.851, 22:19:46.047, 22:21:23.661), and none answered within two seconds. `[reading] play at` is logged only after the wait (`reading-view.tsx` awaits `sync.wait('play')`), and the press itself is not logged, so the gap is measured from the run's first line.

With no network at all the same day, the run failed at once: `11:18:46.578 run against` → `11:18:46.598 foreground: error (Cannot reach …: The Internet connection appears to be offline.)`, and likewise at 11:20:02 (33 ms) and 11:23:29 (19 ms). Expo's fetch uses `URLSessionConfiguration.default` (`node_modules/expo/ios/Fetch/ExpoFetchModule.swift`), with no `waitsForConnectivity`, so a phone with no path fails the request at once, and Play does not wait then.

With Sync off, `createPositionsTransport`'s run returns null on its first line (`if (!deps.enabled()) return null`), so Play's wait ends at once.
