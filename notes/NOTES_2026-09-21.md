## The three font "kinds" did change a Chinese book, and issue #12 said they did not (2026-09-21 00:18)

Issue #12 was written claiming `READING_FONTS`' three entries do nothing on a Chinese book, because Georgia, Times New Roman and Helvetica carry no Chinese glyphs. That is false, and `highlighter.ts`'s own comment above the list already said so: WebKit resolves `font-family` **per script**, so the generic family at the end of each stack is what a Chinese run gets. `Georgia, "Times New Roman", serif` sets Latin in Georgia and Chinese in the system's serif CJK face, in the same paragraph — and `Helvetica, Arial, sans-serif` gives it a modern one instead. The two kinds were already different on a Chinese novel.

`test/renderer/appearance.test.ts` enforced two rules: every stack ends in `serif` or `sans-serif`, and no stack matches `/[一-鿿]|PingFang|Songti|Heiti/`. Reading the reasoning rather than the assertion showed the two were not the same claim. The danger described — "a font that has no glyphs for it" — is a stack that *terminates* at a Latin face, and `"Songti SC", serif` does not: it wins where it has glyphs and keeps the generic behind it. So the first rule stays and the second goes (ADR 0029), which is what lets the list name 宋体 and 楷体 at all.

The correction cost nothing to find and would have cost a wrong feature to miss: acting on the issue as written would have replaced the kinds with six Latin faces that change nothing for the books this app was built to read.

## Android answers `null` for a missing file's size too, so the declaration and the docs are what is wrong (2026-09-21 10:43)

The 10:12 entry called the `null` iOS's. Android's `FileSystemFile.size` is `Long?` and returns `null` unless `file.exists()` (`android/…/FileSystemFile.kt:174`), and `Property("size")` passes it through (`FileSystemModule.kt:243`). Both native implementations agree; only `NativeFileSystem.types.d.ts` (`size: number`, "0 if the file does not exist") and the v57 documentation say otherwise. It cannot reach OpenReader's logic: `lookup` rejects `null` and `0` alike, and every other `.size` read (`document.ts`, `library.ts`, `document-cover.ts`, `runtime.ts`, `reader-file-system.ts`, `audio-files.ts`) comes after an `exists` check or a successful `open()`, which throws for a missing file, and `saveClip`'s now comes after `moveSync`, which throws if the move fails.

## text-size-adjust multiplies every size a Document sets, in the reader's own section frame (2026-09-21 11:34)

First seen before the plan was posted on #17 (10:56), and re-run here on the final tree with the app's own text-size-adjust rules taken out of `#openreader-highlight` for the duration and put back afterwards. The short fixture's first section, a plain paragraph, an added `12px` paragraph and an added `x-small` span:

| rule | paragraph | 12px | x-small |
| --- | --- | --- | --- |
| none | 16px | 12px | 10px |
| `html { -webkit-text-size-adjust: 150% }` | 24px | 18px | 15px |
| … 75% | 12px | 9px | 7.5px |
| … 106.25% | 17px | 12.75px | 10.625px |
| … 200% | 32px | 24px | 20px |

`getComputedStyle().fontSize` reports the adjusted size, so the Document's own size is the computed one divided by the percentage in effect. With the Document's own `body { -webkit-text-size-adjust: 100% }` added, the root-only rule at 150% left everything at 16/12/10 and a span nested as `0.5em` inside `2em` at 16px; the same 150% declared on `html, body, body *` gave 24/18/15 and 24px for the nested span, so a value declared on every element is applied once and does not compound. Rules removed: 16px, and the root back at the app's own 100%.

## CSS `zoom` is no way round it on either device, and the mobile content mode is (2026-09-21 12:02)

Measured in the section documents with the app's own text-size-adjust lines taken out for the duration and put back afterwards.

**On the iPhone 16, `zoom` enlarges everything, including the width.** epub.js gives each section's `body` an inline `width: 393px; padding: 0px 32.75px; box-sizing: border-box`, so `html { zoom: 1.25 }` or `body { zoom: 1.25 }` laid the text out at the old width and scaled it: a paragraph 328px wide became 409px in a 393px frame (`scrollWidth` 491), with the lines unchanged. `body { zoom: 1.25; width: auto }` reflowed it instead: body 393px, paragraph 311px, 6 lines instead of 5, and at `zoom: 2` 262px and 12 lines. ### Which epub.js OpenReader runs, and which one was used

OpenReader depends on `@epubjs-react-native/core ^1.4.8` (installed 1.4.8). That package does not depend on `epubjs`; it **embeds** its own build as a JavaScript string in `lib/commonjs/epubjs.js` (487,001 characters; `lib/commonjs/jszip.js` likewise, 227,163) and, in `Reader.js:71`, writes it to `${documentDirectory}/epub.min.js` on every mount; the template (`lib/commonjs/template.js:18`) loads it with `<script id="epubjs">`. No CDN is involved. The embedded bundle's `EPUBJS_VERSION` is `"0.3"`, which is upstream's hard-coded constant, not the package version, so the exact patch level is not recorded anywhere in the bundle. Fingerprints match npm `epubjs@0.3.93` on every count checked (`allowPopups` 9/9, `allowScriptedContent` 9/9, `supportsSrcdoc` 3/3, `hooks.serialize` 9/9, `fixMiss` 3/3, no `calibreCompat`), the bundle carries core-js 3.18.3 polyfills, and after stripping whitespace it is 242,905 bytes against 220,270 for the npm dist — the same code base, a different build. ### Mechanisms found, ranked by what they do to a crossing position

1. **`.html` members + self-closing non-void tags** (R packages, 21 of 25 sections): the trees differ from the first such tag onward; 50 same-path-different-element cases, 1,645 of 2,422 OpenReader CFIs unresolvable in Zotero, 1,484 of 2,207 Zotero paths unresolvable in upstream. Silent and wrong, not merely lossy. Zotero's own CFIs are unaffected (it never HTML-parses); it is OpenReader's load path (`Section.load` by extension + `srcdoc`) that diverges from the file.
2. **`<table>` without `<tbody>`** (Bruce ch11, 1 of 17 tables): HTML parsing inserts `<tbody>`, every cell path gains a step; `toDisplayedRange` null, mapper prefix-matches the wrong cell except for the first. Same class as 1 (HTML fix-ups), rarer.
3. **Container element as a Block** (Bruce: 216 `<li>` with a nested list, 23 `<caption>`; the `<body>`/`<div>`-with-block-children cases the findings file predicted): mapper null → segment 0 on the idle path, no-op on the active path. Zotero's DOM resolver still finds the element.
4. **`<dl>` definition lists** (Bruce 572, R packages 34+): a Zotero worker quirk — the `<dd>` paragraphs are missing from the SDT (processor v2), so any position inside them collapses to the `<dt>`-words block.
5. **Text-only differences on the same node**: `<br/>` (仙逆 2,061), image `alt` inside a block (Bruce 65 `<pre>` callouts; 2,164 image-only blocks Zotero has and OpenReader has not), `display:none` (仙逆 1 — OpenReader honours CSS, the worker cannot). Harmless for naming the block; they matter only to anyone comparing texts to confirm a match.
6. **Text-step paths** (Zotero → upstream): 430 of Zotero's leaf blocks in the two O'Reilly books are anchored at text nodes; upstream resolves 81 of them correctly, mis-resolves 114 and fails 235. Element-anchored paths do not have this problem.
7. **MathML**: 84 block-level `<math>` elements OpenReader reports as Blocks map into the enclosing Zotero paragraph (prefix); the 10 MathML sections otherwise agree once jsdom's style crash is worked around. No tree divergence was seen from MathML in the HTML reparse.

Not observed in any of the four books: a `<style>`, `<link>` or `<title>` inside `<body>` (the sanitiser shift), a `<p>` with block children (HTML auto-closing), a section without `<head>`, an HTML fix-up in an `.xhtml` member (element counts before and after the `srcdoc` reparse were equal in all 2,096 `.xhtml` sections).

### Verdicts

**OpenReader element CFI → Zotero (the direction the sync needs).** For an EPUB whose members are `.xhtml`, an upstream `cfiFromNode(element)` CFI names the same block in Zotero: 121,376 of 121,376 paragraph/heading Blocks across the two brief books resolved to the identical Zotero leaf block through both the SDT mapper (the resume path, no DOM) and `toDisplayedRange`, real assertions included, whether nested in `div`s, `blockquote`s or carrying inline markup; the spine component agreed on all 2,096 sections. The trust breaks along one seam — anything that makes OpenReader's HTML-parsed tree differ from the file — which in practice means `.html` members with self-closing tags (an entire O'Reilly book off by one paragraph, silently) and `<table>`s without `<tbody>` (one in seventeen); and it degrades, without lying, when the Block is a container Zotero splits (`<li>` with a nested list → segment 0) or a `<dd>` paragraph (→ the `<dt>` terms). So: trustworthy for `.xhtml` books and for `<p>`/heading/`<pre>`/`<td>` Blocks; the sender should carry the block's text so the receiver can refuse a mismatch, strip or keep only true assertions, and treat `.html` members and container Blocks as the cases that need a text check rather than a path.

**Zotero block path → upstream epub.js.** An element-anchored Zotero leaf path resolves to the same element in upstream for `.xhtml` books (125,533 of 125,533 paragraph/heading blocks in A and B, the only differences being image alt text and `<br/>` whitespace) and fails for the same HTML-parse reasons in `.html` books (1,484 of 2,207 in R packages). But Zotero also anchors leaf blocks at **text nodes** whenever a container holds bare text (430 such blocks in the two O'Reilly books, none in the novels), and those paths follow the spec's text-step numbering that upstream's resolver does not implement: only 81 of 430 resolved to the right node. So a Zotero path can be trusted in upstream only when it ends in an element step and the book is `.xhtml`; a text step must be dropped to its parent element (or the Zotero-side text carried) before it is handed to epub.js.

## The phone side of position sync, built: what was measured on the way (2026-09-21 17:50)

Issue #20, the phone half of `docs/spec/SYNC-FORMAT.md` (plugin repo). Three facts found while building it, none of them design.

- **The React Compiler lint refuses a transport built in `useMemo`.** `react-hooks/refs` ("Passing a ref to a function may read its value during render") and `react-hooks/purity` (`Date.now` in a closure) both fire on `createPositionsTransport({ enabled: () => settingsRef.current…, now: () => Date.now() })` inside `useMemo(…, [])`, although nothing there runs during render. `use-reading.ts`'s `clock` object, which reads `bridgeRef.current` inside methods, is not flagged — the difference is the object being *passed to a function* in render. `use-sync.ts` therefore makes the transport lazily, on the first poke, inside a `useCallback`; the lint is silent on that and the behaviour is the same.
- **The shared fixture round-trips byte for byte**, including the `pdf` item this build cannot use: `serializePositionsFile(parsePositionsFile(text).items) === text` for the 594-byte `test/core/sync/fixtures/xujialiu-positions.v1.json`, which the plugin's suite holds as the same bytes. Merging the file into itself is the identity.
- **The bundle builds.** `expo export --platform ios` over the changed tree produced a 4.9 MB Hermes bundle with no missing-module error; the simulator run is the tester's (`docs/install-on-simulator.md`). `npm test` 1,281 passing in 77 files (up from 1,264 in 73), `typecheck` and `lint` clean.

Two shapes changed under the tests rather than in the design: `readingPositionAt` now takes the Stamp (`readingPlaceAt` is the four-argument form the renderer uses, `stampPlace` joins the two), and `handleBlocks` hands the resume attempt to one `tryResume` so a place arriving from another device is tried the same way the one the book opened with is — the structural pins in `test/app/player-rules.test.ts` moved with it.

## The phone side on the iPhone 17 simulator: seven checks pass, two defects in when a sync runs, three small ones (2026-09-21 19:59)

The ios-tester's run over the tree of the 17:50 entry, Metro on port 8084, no native rebuild. Its measurements, then the two defects with their causes; the fixes are in the same tree and pinned by `test/app/use-sync.test.ts` and `test/app/sync-rules.test.ts`.

**Measured.**

- **Play waits for the folder, bounded.** Against a stub that stalls every GET six seconds, Play-to-playing was **2.44 s, 2.90 s, 2.42 s**: the 2 s bound of `use-sync.ts`, plus synthesis. Against the owner's real server, **1.43 s**.
- **An adopted place moves the paused highlight within 4 s of foregrounding**, through `resumeAt` → `tryResume` → `seekTo`.
- **A late adoption does not move a playing reading.** The stub was swapped mid-playback for an item stamped two hours ahead; after 15 s the highlight was on the natural next paragraph, and the Library entry carried the inherited stamp — so the adoption landed in the file and the shelf and was declined by the reading, which is the rule.
- **A version-1 `library.json`** was read with its positions at the oldest Stamp and rewritten as version 2 on the first change.
- **`toLocaleTimeString` renders a time on Hermes** — the status line's "Synced at 17:31" is real.

**Defect 1 — turning the switch on never ran the first sync.** `sync-screen.tsx` called `setSettings({ …enabled: true })` and `sync.poke('switch-on')` in the same tick. `createSingleFlight.poke` runs synchronously, the run's first line reads `deps.enabled()` → `settingsRef.current.sync.enabled`, and that ref is updated in a passive effect after the re-render — so the poke saw `false` and skipped. Measured: folder empty, switch on, check passed, twelve seconds later the server still answered 404 and the status line was blank. Fixed in `use-sync.ts`: an effect declared **after** the ref-updating one pokes `'switch-on'` on the false-to-true edge of `settings.sync.enabled` (effects run in declaration order); the screen no longer pokes. The hook test mounts the real hook and counts one run, with `enabled` seen as true.

**Defect 2 — a self-sustaining sync loop.** `useSync` returned one object memoised on `[poke, wait, last, check]`, and `last` changed after every completed run; the shell's launch effect depended on that object and poked again on each completion — **five GETs in thirty seconds** with nothing to upload, and against the real server the loop adopted a hand-placed item 200 ms after it was PUT, with no user action. The `AppState` effect re-subscribed on the same churn. Fixed: `useSync` returns a **stable** `{ poke, wait, check }` handle and the last outcome beside it; the shell carries `syncLast` separately and nothing that pokes may name it in a dependency list (pinned). The hook test counts one download over three settled rounds with the shell's exact launch effect.

**Three smaller ones.** (a) A version-1 position went out as `"stamp":{"at":0,"device":""}`, which spec 6.2 forbids, so no reader could adopt it: `itemsOf(entries, device)` now signs such a position with this device's name and leaves `at` at 0. (b) After an adoption — and after the ordinary resume at open — the cursor moved, `status.utterance` changed, and `reached` re-stamped the **same** place `{ at: adopted + 1, device: 'iPhone-…' }` (**+200 ms and +473 ms** after the desktop's stamp): the phone claimed the desktop's place, uploaded it, and the desktop would have adopted its own place back under the phone's name. `use-reading.ts` now remembers the Utterance a resume landed on (`resumedAtRef`) and `readingPosition()` answers null while the cursor is still there; the ten-second write, the pause write and the unmount write all skip it, and `reading-view.tsx` drops the place it holds for the way out when that happens. (c) The Sync screen's folder line outlived the folder: `folderMissing` had priority over the last outcome until the screen was re-entered. It is now derived — shown only while `syncLast` is still the outcome the check saw — because the React Compiler lint refuses a `setState` inside an effect (`react-hooks/set-state-in-effect`), and a fact that follows from the run's completion needs no effect to chase it.
## The simulator has a volume of its own, and it is a file (2026-09-21 20:45)

Every booted device keeps `~/Library/Developer/CoreSimulator/Devices/UDID/data/var/run/simulatoraudio/audiosettings.plist`, holding `sim_input_device_uid`, `sim_output_device_uid`, `sim_ringer_state` and **`sim_volume`**, default **60**. That 60 is the `0.6` an earlier run read and could not move: an app on that device reports `AVAudioSession.outputVolume=0.6` while the file says 60, and `0.0` when the file says 0.

Measured on a throwaway iOS 27.0 device with a 40-line iOS app playing a 440 Hz tone through `AVAudioSession(.playback)` and `AVAudioEngine`, and a CoreAudio process tap (`CATapDescription(stereoMixdownOfProcesses:)` plus a private aggregate device) recording what that guest process delivered to the host. `sim_volume` **60**: peak **0.090000**, rms **0.063639** over 286,720 samples in 3 s. `sim_volume` **0**: peak **0.000000**, rms **0.000000** over 286,720 samples. The Mac's own output was muted throughout and never touched, and the tap reads the process's stream, so neither number depends on it. 0.25 amplitude arriving as 0.090 is 0.6 twice over: the guest applies its volume, and so does the route.

Two limits, both measured. A boot rewrites the file with the defaults — 0 before `simctl shutdown`, still 0 in the file afterwards, **60** after the next `boot`. And the value is taken when an app activates its audio session: flipping 60 → 0 under the probe **while it played** left the tap at peak 0.090000, and the next launch read 0.000000. So: boot, set, launch.

The dead ends. macOS lists each simulator app as its own host audio process object (`kAudioHardwarePropertyProcessObjectList` showed `top.xujialiu.openreader` with the device's own bundle path, `IsRunningOutput=1`), but `AudioObjectIsPropertySettable` answers no for volume and mute in all three scopes — there is no per-app mute to script. Xcode 27's DeviceHub has "Enable audio output from devices", one switch for every simulator, whose container `defaults` refuses to write and whose process has no menu bar for AppleScript ("Can't get menu bar 1 of process DeviceHub. Invalid index."). `xcrun simctl` has no audio subcommand; `simctl io UDID enumerate` prints the `com.apple.CoreSimulator.Audio.HostRoute` port with `Guest Audio Output -> Default Host Audio Device` and the host devices it could use, but only screens can be changed, and the setter behind it (`routeGuestDeviceScope:toHostDeviceUID:completionQueue:completionHandler:` on `SimAudioHostRoutable`) is private and would still need a silent host device to point at. No app-side test hook was needed, so none was added (#21).

## Second simulator run: the five fixes hold, and two more defects in what a place does after it arrives (2026-09-21 22:30)

The ios-tester's second pass over the 19:59 tree. What it measured, then the two defects and their fixes (pinned by `test/app/use-reading-resume.test.ts`, the first test in this repo to mount `useReading` itself, and by `test/app/sync-rules.test.ts`).

**Measured.** The switch's first sync took the folder from 404 to 200 within 2 s; **0 requests in 113 s** of idle foreground; no PUT after a pause inside the adopted sentence; a skip away and back re-stamped, as it should; version-1 items went out under `iPhone-…`. And the cross-product resume itself: the fixture opened **from the Library** landed on the desktop's exact sentence.

**Defect 3 — an adopted place in an unrendered section never lands.** The fixture handed over with `xcrun simctl openurl` while nothing was open: the Document Id matched, the desktop's place (`epubcfi(/6/6!/4/2/4)`) was adopted into `library.json`, and the reader opened at chapter 1 with no highlight and stayed there **sixteen minutes** — `utterance=null section=null rendered=1/3 resume=null` — reproduced twice; six swipes later the pending place landed (`utterance=34 section=2 rendered=2/3`). Cause: `resumeAt` with nothing landable leaves the place pending, `tryResume` fails on each report of another section and keeps it pending, and nothing asks epub.js for the section the locator names — `<Reader initialLocation>` does that for the place a book *opens* with, and an adopted place arrives after that. Fixed: `revealPendingPlace` reads the spine index off the locator (`/6/N` → N/2 − 1, the rule both readers were measured to share at 17:11) only to ask whether that section has reported a Block, and hands the whole CFI to the bridge's `goTo` — the same currency a contents row uses — from `resumeAt`, and again on each report that fails while an adopted place is pending (an ask sent before the page could hear it is not lost), never for a section that has reported. ADR 0019's claim rule stands: a tap, a skip, Play or a contents row drops the pending place, and a section arriving after that moves nothing.

**Defect 4 — leaving a book re-stamps a place that did not move.** A pause at 21:39:16 wrote stamp `1789997956288`; leaving the reader at 21:48:03 wrote the same locator and the same sentence again as `1789998483390`, and it went up to the owner's real file — the phone won a merge it should have lost (ADR 0031). The unmount write, and equally the pause write, sent whatever `positionRef` held. Fixed at the one place every write goes through: `reached(id, place)` in `use-library.ts` returns without writing when the entry already holds a position with the same canonical locator and the same `anchor.exact` (`samePlace` in `sync-items.ts`); the desktop's Stamp stands, and so does the phone's own last one.
