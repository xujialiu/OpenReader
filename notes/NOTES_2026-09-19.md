# 2026-09-19

## Hermes: what the engine in React Native 0.86 actually has

Measured, not inferred. Hermes **250829098.0.17** — the engine RN 0.86.3 bundles —
debug build, iOS 27.0 simulator. The check lives at `src/spike/hermes-support.ts`
and runs on the app's first screen, so it can be re-run whenever the engine
changes.

| Feature | Result | Why it was in doubt |
|---|---|---|
| `String.prototype.normalize('NFKC')` | **yes** | Has crashed on Hermes historically; absent from recent release notes. Verified against fullwidth Latin, a circled digit, an fi ligature, a CJK compatibility square and a no-break space. |
| `TextDecoder` | **yes** | Release notes of 2026-06-05 said it now ships with the engine; an older issue said otherwise. It exists, reports `utf-8`, decodes 3- and 4-byte sequences, and keeps state across a chunk boundary with `{stream: true}`. |
| `normalize('NFC')` / `('NFD')` | yes | Needed by the text anchors of ADR 0008, since EPUB text may arrive either way. |
| `\p{L}`, `\p{Script=Han}` | yes | Load-bearing in the word aligner being ported. |
| **`Intl.Segmenter`** | **NO** — `Intl.Segmenter is not a function` | Hermes ships a cut-down `Intl`. |

**Both open questions from ADR 0001 resolve favourably.** Nothing in the ported
aligner needs a polyfill or a JavaScriptCore decision.

The new finding is the last row, and it changes two things. `unicode-segmenter`'s
`intl-polyfill` is **required**, not a hedge — and item 7 of the verification list
loses half its meaning: there is no platform `Intl.Segmenter` whose sentence
quality could be judged. What gets judged is the polyfill's.

## Expo SDK 57 cannot launch on iOS 27 as generated

`npx expo run:ios` builds and installs, then iOS refuses it:

```
Application failed to launch: UIScene life cycle is required for apps built with this SDK.
```

The generated `AppDelegate.swift` still creates its own `UIWindow` from
`UIScreen.main.bounds`, and the generated `Info.plist` has no
`UIApplicationSceneManifest`. Adding the manifest key alone was tried and iOS
still refused.

Expo already ships the answer and has not wired it up:
`node_modules/expo/ios/AppDelegates/ExpoAppSceneDelegate.swift`, whose own doc
comment reads *"Required by the iOS 27, which asserts at launch unless the app
adopts the scene-based life cycle."*

`expo@57.0.24` is the newest release on the `sdk-57` tag, so there is no patch
release to wait for; SDK 58 is still in preview. The fix that was verified end to
end, and what to do about it, is ADR 0018.

## Confirmed for the provider port

The Zotero-TTS provider suite — 20 files, **381 tests** — passes **unchanged**
under this project's vitest 5.0.1, run against that repo as root. That is why the
layout here mirrors it exactly (`src/core/providers/` under `test/core/providers/`)
and why vitest 5 was pinned rather than matching that repo's 4.1.10.

`test/setup.ts` replaces global `fetch` with one that throws, so a provider test
that forgets to inject a fake fails instead of quietly calling a real provider.

## Loose ends noticed while scaffolding

- **Pods carry mixed deployment targets** (164 at 15.1, 32 at 16.4, 4 at 17.2),
  which is normal. But Expo's `ios.deploymentTarget` writes only the **app
  target's** configs — the project-level configs stay at 16.4, so any target added
  later (a widget, a share extension) inherits 16.4 rather than 17.2.
- **TypeScript is 6.0.3 here and 7.0.2 in Zotero-TTS.** Expo's template pins ~6.0.3
  and `typescript-eslint` caps below 6.1, so the ported code may need to compile
  under an older compiler than it was written for.
- **One unexplained test failure.** An import-boundary assertion failed once during
  a concurrent Xcode build and has passed every run since. Not reproduced, not
  explained. The suite now asserts that the lint override actually resolves, so a
  recurrence names its cause.
- `bundleIdentifier` is `top.xujialiu.ownreader`, guessed from a domain. No licence
  file has been chosen yet, though ADR 0006 assumes the licence is free.
